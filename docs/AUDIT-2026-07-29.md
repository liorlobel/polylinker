reviewer's wording — and it frequently did: refuters confirmed the defect while

**Six refuters died mid-response** — connection errors, not analysis — in these

- `fileio-genbank` — the SnapGene long-qualifier finding was verified end to end
  against the real `pKoV with His decR.dna`, including a byte-level check of
  block 10 confirming the file uses **only** the long spelling (10
  `<Qualifier>`, 10 `<QualifierValue>`, zero `<Q name=`). See spot-check 4.
- `enzymes-clone` — the second-priming-site finding was reproduced through
  `pl_clone::pcr` on a template built to carry the 3'-seed twice and the full

The remaining under-scrutinised findings (`core-translate-orf`,
`features-annotate` ×3, `gui-seqedit`) were each read against the code during

## Cross-area requirements closed here (24)

These are the defects no area agent could fix, because the broken thing and the
thing that had to change were in different lanes. Each was verified by execution
after the change, not only by test.

### 1. `crates/pl-core/src/oplog.rs` — silent-data-loss — fixed

`remap_annotations`' `a` fallback rescued a start that had died inside a deleted
region on the strength of `s_end >= old_end` — a test that reads "the far end
lies past the edit and therefore survived", a conclusion only a coordinate that
names a real base can support. `gene 5..20` on a 12 bp molecule names eight
bases that do not exist. Deleting every base produced `gene 1..8` **on a
molecule with no bases**, and worse, it *laundered* the report: `validate()`
went from one `PastEnd` to zero, `refuse_new_problems` reads that as an
improvement and commits, `genbank::write` then emits `gene 1..8` under a `0 bp`
LOCUS, and `Molecule::is_annotation_track()` answered true for a document the
user had merely emptied — which is what left `pl-gui`'s sequence editor refusing
to edit it.

Fixed by guarding that one fallback with `s_end <= old_n`. Deliberately not a
blanket "out of range is not an anchor": an out-of-range end whose *start*
survives is still shifted, absurd value and all, so `validate()` goes on
reporting it instead of being quietly truncated. Both directions are pinned.

*Reproduction, before:* `Segment { start: 1, end: 8 }` on a zero-base molecule.
*After:* the feature is dropped with its bases, `is_annotation_track()` is false.

This is the true location of the finding filed against
`bins/pl-gui/src/seqedit.rs:91`. The `pl-gui` agent **refuted** that filing,
verified the relocation empirically with a scratch program, and declined to
change `Editability::of` — correctly: returning `Editable` there would hand the
user a caret and then the raw engine refusal.

### 2. `crates/pl-fileio/src/genbank.rs` — correctness — fixed

`location_parts` took the origin-crossing branch for `end < start` and emitted
the second part as `1..{end}`. With `end == 0` that is `1..0`, a range whose low
bound exceeds its high one and which therefore names no base. It reached the
file: `<Segment range="5-0"/>` on a 16 bp molecule wrote
`misc_feature join(5..16,1..0)` at exit 0 with nothing on stderr. Biopython does
not reject it — it "fixes" it into a feature spanning the whole molecule, so a
coordinate naming nothing became an annotation over everything.

Refused and reported rather than clamped to something plausible. `pl-core`'s
`validate()` now reports the shape too, but `bins/pl` never called `validate()`,
which is finding 3.

### 3. `bins/pl/src/main.rs` — silent-data-loss — fixed

`Molecule::validate()` was reached from exactly **one** place in the whole
workspace — `pl-gui`'s document loader — so every check it performs was
invisible from the terminal. The reachable case is dull and common: a GenBank
record whose `//` terminator is missing and which has anything after the
sequence. The ORIGIN loop reads on to end of file, so a 12 bp record with a mail
footer loads as `acgtacgtacgt--SentfrommyiPhone`, 30 bases, against a LOCUS line
that says 12 — and `pl info` printed both numbers without once remarking that a
file disagreeing with itself is a file to look at.

New `note_self_contradiction`, wired into `pl info` (both output paths) and
`pl convert`. A notice, not a refusal.

*Verified by execution:*
`pl: foot.gb: the file declares 12 bases but carries 30`, with an ordinary file
saying nothing — a notice that fires on every file is a notice nobody reads.

### 4–7. `Feature::extent` consumers — correctness — fixed

`Feature::start`/`end` are a min and a max over the segments. `genbank::write`
emits an origin-crossing feature as `join(2677..2686,1..7)`, so the minimum start
is *always exactly 1* and the maximum end *always exactly the molecule length*.
`pl-core` added `Feature::extent` in its own lane; **no consumer had adopted it.**

- **`pl info --json`** reported a 17 bp promoter as `"start": 1, "end": 2686`,
  spanning the whole plasmid, with only `"segments": 2` beside it and the true
  coordinates unrecoverable from a shipped machine-readable format. *Verified:*
  now `"start": 37, "end": 7` on a 40 bp circle; an ordinary spliced join still
  reports its min/max, which is the control.
- **`pl-gui` "Set origin at selected feature"** issued
  `Rotate { origin: f.start() }`, always 1 for such a feature, which hits
  `if shift == 0 { return true; }`. The button reported success, pushed an undo
  entry and dirtied the document while renumbering nothing — and the one feature
  a user most wants to rotate to the front is exactly the one that straddles the
  origin.
- **`pl-gui` feature-list panel** labelled that 17 bp promoter `1..2,686`, in the
  panel whose entire job is saying where things are.
- **`crates/pl-wasm`** shipped the same collapsed pair to the browser.

`map.rs`'s lane packing was **left alone** and is recorded under Deferred: the
drawing itself is already correct (it goes through `segs`, which `pl-gui` rebuilt
this pass on `pl_draw::ranges`), and the residue is cosmetic lane width.

### 8. `bins/pl` — correctness — fixed

`pl orfs` omitted `Orf::laps` from both output paths. `start..end` is an
inclusive span round the circle and stops being the ORF's extent the moment
`laps > 0`: on a 19 bp circle a 33-base ORF printed `5..18  10 aa`, a range of
14 bases, with `start < end` so not even the wrap was visible. `bases_of` in the
same function already used `o.bases()`, so `--translate` printed all ten residues
while the coordinates on the line above were a whole lap short — one line
disagreeing with itself.

JSON gains `bp` and `laps`; the text form gains a lap note.
*Verified:* `{"start": 5, "end": 18, "bp": 33, "laps": 1, ...}` and
`crosses origin, and laps the molecule 1 more time(s) — 33 bp in all`.

Audit 2026-07-28 #6 added `Orf::laps` and `Orf::bases()` to `pl-core` and
stopped there. `pl-mcp` and `pl-py` were fixed in their own lanes this pass;
`bins/pl` was the last reader, and its `--json` output was the artefact that
audit quotes as the defect.

### 9. `bins/pl` — silent-data-loss — fixed

`pl digest`'s unknown-enzyme guard was per **call**, not per **name**: `retain`
followed by `if results.is_empty()` fires only when *every* name is unknown. So
`pl digest x.fa --enzyme HaeIII --enzyme EcoRI` printed the EcoRI row, exited 0
and dropped HaeIII without a word — an answer about one enzyme under the heading
of two. DpnI and HaeIII are both absent from the 58-row table and both ordinary
things to ask for, so this is reachable by typing a *real* enzyme name.

Every name is now resolved through `pl_enzymes::by_name` before anything is
digested, and all misses are named at once. `bins/pl-mcp` and `crates/pl-py`
already resolved per name; `bins/pl` was the odd one out of three.

*Verified:* refuses naming HaeIII, prints no partial answer, and a genuine
non-cutter (`NotI`) still reports no cuts rather than being confused with an
unknown name.

### 10–11. `pl_thermo::anneal_sized` adopted — correctness — fixed

`pl-thermo` added `anneal_sized` in its own lane and said plainly that the
user-visible output would not change until two call sites outside that lane
moved. They have.

The Phusion/Phire note reads *"Ta = Tm + 3 for primers over 20 nt"*, and the
length-blind `anneal` applied that +3 at every length — so the advice
contradicted its own stated condition **on one printed line**.

- **`bins/pl` `cmd_tm`** folded its Tm list to a bare `f64`, discarding the
  length one line before the rule that needs it. *Verified:* the 18 nt SP6
  primer `ATTTAGGTGACACTATAG` (Tm 38.9 °C) advised **42 °C** before and **39 °C**
  after; a 24 nt oligo still gets its +3 (57.8 → 61 °C), which is the control
  that stops the fix degenerating into "never add three".
- **`crates/pl-design/src/report.rs`** had the same call, and it bites harder
  there because `Constraints::LEN_OPT` is 20 — the scorer aims at exactly the
  length at which the carve-out turns on, and a `pl design` user is being handed
  a protocol to run. Uses the **footprint** length, not the ordered oligo's: the
  block scopes itself to the early cycles, when only the footprint is templated.

### 12. `crates/pl-index` — silent-data-loss — fixed

`ENGINE` bumped 2 → 3. The `ENGINE` doc states the rule — *"bump this by hand
whenever parsing or derivation changes"* — and this pass met both halves of it:
`pl-fileio`'s reader learned the long qualifier spelling, and
`pl_scan::searchable_text` indexes qualifier keys and values. Without the bump a
library built before the fix keeps rows in which those qualifiers were never
indexed, reports them as `unchanged (reused)` on the next scan, and
`pl find --text` goes on answering that a translation nobody can find is not
there.

### 13. `reference/python/snapdna.py` — oracle blind spot — fixed

The Python cross-check oracle matched only `<Q>`/`<V>` — **the same blind spot as
the Rust reader it exists to check.** So on an export-10 file the two agreed
perfectly about a feature set from which *both* had silently dropped every
qualifier. An oracle sharing the implementation's blind spot certifies the loss
instead of catching it, which is exactly what happened. Now accepts both
spellings and both attribute vocabularies, and records a valueless qualifier
(GenBank's bare `/pseudo`) as present-with-no-value rather than absent.

### 14. `docs/DNA-FORMAT.md` §5 — documentation — fixed

Documented only the short spelling. That omission is the **upstream cause** of
finding 13 and of the `pl-fileio` finding it mirrors, not a documentation
nicety: two independent implementations both matched what the spec file
described. Now records both spellings with the export/import version ranges each
is observed on, and states that a qualifier element carrying no value element is
valueless rather than absent.

### 15. `reference/python/tests/xcheck_motif.py` — missing coverage — fixed

`ours()`'s docstring claimed the differential test ran "over a temp FASTA"; it
only ever passed `--seq` with an explicit `--topology`. That stale claim is
precisely why `pl find-motif`'s **file** path had zero differential coverage and
the topology defect survived to ship. Fixing the docstring is not enough, so the
oracle gained a real leg: it writes a GenBank record and drives `find-motif` with
**no** `--topology`, asserting first that the record came back with the topology
it declared — without that guard the comparison would pass vacuously for every
linear case, which is how the defect survived.

*Verified:* 480 `--seq` comparisons and 480 file comparisons, 0 disagreements.

### 16–17. `crates/pl-draw` reports gain a print site — fixed

`Report::labels_truncated` and `Report::partly_drawn` had **no reader anywhere in
`bins/`**. So the shortening that audit 2026-07-28 #49's fix already performed
happened silently in figures headed for journals — and `pCMV-WP...` is a
different plasmid's name from `pCMV-WPRE`. Half a feature is likewise a worse lie
than no feature: a 101 bp arrow drawn from one segment of
`join(100..200,5000..6000)` is indistinguishable from a real 101 bp feature.
Both now print in `pl export`. The `pl-draw` doc that said "nothing in `bins/`
prints this list yet" was corrected in the same edit, per the house rule.

### 18. `tools/ci.ps1` + `crates/pl-index/tests/purity.rs` — false gate description — fixed

`ci.ps1` said the wasm32 step *"goes red the day a storage concern leaks in"*.
It does not: `wasm32-unknown-unknown` ships the full std filesystem, environment,
subprocess and clock surfaces through its `unsupported` platform layer, so
`std::fs::read` compiles, links, and returns `ErrorKind::Unsupported` at run time
on a target this project never runs. `purity.rs` knew this and said so by
*quoting* the false sentence — so two files stated opposite things about one
gate, and the one a developer reads when the gate goes red was the false one.
`ci.ps1` now describes what it enforces and points at `purity.rs`; `purity.rs`'s
quotation moved with it, so neither is now the stale one.

### 19–20. `prototype/dna-reader.template.html` — silent-data-loss — fixed

- `expGb` and `expFa` discarded their return code and downloaded
  unconditionally, while `dlBtn` beside them had always checked. That stopped
  being harmless once the core learned to refuse a multi-record file: with the
  code discarded, **the refusal message is what got saved**, so the browser
  handed back a file named `plasmid.gb` whose contents were
  `{"error": "this file holds 3 records ..."}`. A refusal that still downloads
  something is worse than no refusal.
- The page rendered none of the four summary fields `pl-wasm` had just taught the
  ABI to carry. `recordsInFile > 1` (you are looking at record 1 of N),
  `topologyDeclared == false` (FASTA records no topology, so "linear" is this
  reader's default and not a claim the file made — the Plasmidsaurus case),
  `suspect` (the blank map is a parse that found nothing, not an empty plasmid),
  and the two `unrepresentable*` lists now all surface.

### 21–22. `features/build/check_signoff.py` + `build.py` — signature integrity — fixed

`Db::parse` trims every signed cell, lower-cases `class` and `boundary_rule`, and
turns an empty `genbank_key` into `misc_feature`. `check_signoff.py` hashed the
cells **raw**. So one trailing space on a description — the sort of thing an
editor leaves behind — made the two implementations of `content_digest` disagree
about a row nobody had edited.

**Measured, and the direction is worth stating precisely because the reviewer had
it backwards.** With a trailing space planted on `PLF:0001`'s description:

- *old* `check_signoff.py` → `1 violation(s) … The approval has lapsed;
  re-read the row and replace its line in features/SIGNOFF.tsv` — a **false
  lapse report**, telling a curator their signature died over whitespace the
  loader trims away.
- *new* `check_signoff.py` → signature intact, because the content that was
  signed is unchanged.
- `Db::parse` (fixed in `pl-features`' own lane) → reports the cell as a load
  error, so the bookkeeping problem is still named and cannot ship silently.

That is the right split: the approval stands, the stray whitespace is a separate,
named, fixable thing. Three new controls pin it, and **all three were proved able
to fail** — reverting only the canonicaliser makes `check_signoff.py` exit 2 with
`CHECK IS WORTHLESS IN THE OTHER DIRECTION: a description padded with spaces
invalidated the signature here`.

### 23. `crates/pl-features/tests/schema_pin.rs` + `build.py` — pin widened — fixed

`pl-features` deliberately did **not** widen this pin in its own lane, and said
why: doing so before `check_signoff.py` was fixed would have made the pin assert
a divergence that still existed. With 21–22 done, it is widened. Every signed
cell in the fixture is now non-canonical — padded with spaces, `class` and
`boundary_rule` in upper case, `genbank_key` empty — while `build.py`'s
`signed_row` holds the canonical row directly. The two sides reach the same
digest from opposite directions:

```
Python (canonical Row)      25b8783590b89116e394a31b946a86432f8139a510d6e0d4db934d2630c9c6e3
Rust   (padded TSV, parsed) 25b8783590b89116e394a31b946a86432f8139a510d6e0d4db934d2630c9c6e3
```

Both pinned literals updated together, as their own comments demand. **This is a
fixture, not the shipped tables**, so no real signature is touched by it.

### 24. `crates/pl-clone` diagnostics reach the CLI — fixed

`pl_clone::cut` returns an empty `Vec` for input that is not DNA, and `bins/pl`
still called it. Nothing was silent — `pl goldengate` refused — but the reason it
printed was misattributed: *"BsaI leaves no overhang here — 0 fragment(s)"* for a
file that was never digested at all. Both call sites now use `try_cut` and report
`CutError::NotDna`, which names the offending character. The bench adapter gains
an `error` key on the failure path only, so the pydna oracle reads exactly what
it read before.

### A stale CI gate that had been red long enough to stop being read

`prototype/check_page.js` asserted `ENZYMES.length === 50`. `pl-enzymes` ships
**58**, and has for some time, so the gate had been failing for a reason nobody
had to act on — which is how a gate stops being read at all. Worse, the
assertion it was making is not the one it wanted: what matters is that the page
takes its enzyme list *from the core* rather than carrying one of its own.

Replaced with a check on that property — the set is non-empty and contains
enzymes only the core's table defines — which still fails if the export is
dropped and does not go stale when a row is added. Writing it also surfaced a
second, quieter defect in my own first draft: `ENZYMES` holds `[name, site]`
pairs, so reading `e.name` yields a list of `undefined` whose *length is still
right* — exactly the kind of green a count-only assertion cannot distinguish from
the real thing. `prototype/dna-reader.html` is generated and untracked; the
tracked template and the checker are what changed.

*After:* `ALL CHECKS PASSED`.

## Refuted at fix time (recorded, because declining a bad fix is a result)

The refuters had already killed 35 findings before any code was written. These
are the additional refutations made *during* fixing, where a finding was real but
its suggested remedy was not, or where a claim did not survive contact with the
code. They are listed because silently doing something different from what was
asked is worse than saying so.

- **`pl-design` / `pair.rs` `cap`** — both suggested fixes were shown to be
  ~800M and ~288M pair builds at 2 Mb. Replaced with `retain_pairable`, one
  binary search per candidate.
- **`pl-design` / `Reason::OffTheEnd`** — the suggested "recast `--flank` as
  something to lower" is a regression: lowering it strictly shrinks both windows.
- **`pl-design` / `specificity.rs` seed panic** — the suggested "fall through to
  `find_bindings`" converts a loud panic into the *silent false-specificity
  claim* of the very next finding. Refused up front instead.
- **`pl-design` / `fold.rs` render** — printing `<=` would read as a gate the
  pair had just failed, because `describe_dg` prints the acceptance conditions
  two lines above with `>=`. Verified empirically: a first draft asserting the
  report contains no `>= -` **failed** on the legitimate threshold line.
- **`pl-gui` / `seqedit.rs:91`** — refuted and relocated to `pl-core`'s
  `remap_annotations`, confirmed with a scratch program rather than by argument.
  Fixed here as cross-area finding 1.
- **`pl-fileio` / GenBank ORIGIN loop** — the suggested
  `if !line.starts_with(' ')` break was measured to break any sequence ≥ 100 Mb
  (`{:>9}` fills all nine columns) and any tab-indented ORIGIN body. Chunked at
  the second `LOCUS` instead.
- **`pl-fileio` / namespace prefixes** — "reject any `:`" would have regressed
  working input; narrowed to "prefix not declared on that note".
- **`pl-fileio` / `<Segment range="13-0">`** — the whole limb was **dropped**: no
  input can reach it, so the suggested guard would defend nothing.
- **`bins/pl` / `--limit` and `min_homology`** — refuted, and a WHY comment added
  at the `--limit` site so a future reviewer does not "fix" it. `--limit` can only
  show *more* rows, never hide a record behind a false claim of absence.
- **`bins/pl` / `pl goldengate` message** — the alleged sibling false text does
  not exist; `grep -rn "Type IIP" bins/` had exactly one hit.
- **`bins/pl` / `overhangs.len() < 2`** — would suppress real faults; a single
  overhang still reaches the palindrome check.
- **`bins/pl` / `is_annotation_track()` predicate** — false for the reviewer's own
  reproducer, which declares 4000 bp. Used `seq.is_empty()`.
- **`pl-core` / `Feature::start`/`end`** — **not** made `Option` and not changed:
  they are correct and conventional for an ordinary multi-exon join. `extent` was
  added beside them.
- **`pl-core` / `a >= 1` conjunct** — simply deleting it regresses an existing
  test by leaving a phantom `0..0` stub.
- **`pl-clone` / `left_end`/`right_end` bounds guards** — audit #43 explicitly
  considered and rejected these; re-adding would re-hide the source.
- **`pl-clone` / `cut` byte-slicing** — the reviewer's fix leaves the real defect
  (four phantom bases appended before any slicing) in place.
- **`pl-features` / the `unseedable` polarity** — the suggested doc wording had it
  **backwards** and would have replaced one false sentence with another.
- **`pl-features` / the implied-diagonal check** — proved a no-op on the finding's
  own fixture; anchored `best_end` instead.
- **`pl-index` / `", fs"` and `"{fs"` in `BANNED`** — fires on `fn f(a: u8, fs:
  &Store)`, `let (n, fs) = ..`, and `format!("{fs}")`, and the `BANNED` self-test
  structurally cannot notice.
- **`pl-scan` / `ErrorKind::NotFound` carve-out** — Rust maps three distinct
  Windows errors to `NotFound`, so the kind cannot separate "the files are gone"
  from "the road to them is". Fixed unconditionally.
- **`pl-scan` / breadth-first `walk`** — the reviewer's stated memory cost is
  false; the documented order is the costlier one everywhere the two differ. The
  *comment* was the defect.
- **`pl-doc` / the `\` line continuation** — compiled and shown to yield
  `claimed.Limits:`, destroying the paragraph break `pl methods` paginates on.
- **`pl-draw` / `xcheck_eps.py`** — refuted with a real run: the re-encoding
  prolog does **not** trip the EPS gate, because every prolog line begins with
  `/` or `%`. `problems: 0`, exit 0. No change made.
- **`pl-mcp` / `pl orfs --json` as a reference for `laps`** — it was not one;
  `laps` was absent there too. Fixed in this phase as cross-area finding 8.

Per-crate green was not taken as proof, and neither was a passing test written by
the agent that wrote the fix. The five highest-severity findings across all areas
were reproduced against the built binary.

**1. `bins/pl` — `find-motif` discarded the file's declared topology.**

with `/Odieresis`, `/adieresis`, `/Aring` and `/endash` present in the

The survivor counts are the **pre-`cap`** figures, which is the second half of

## Deferred (3)

Each of these is a real item that was **not** closed, with the reason. None is a
silent omission.

### D1. `crates/pl-core::Segment` needs `name: Option<String>`

`<Segment name="-35"/>` is dropped on read, so
`<Feature name="lac promoter"><Segment name="-35"/><Segment/><Segment
name="-10"/>` comes back as three indistinguishable anonymous boxes. Measured: 7
segments across 6 of 51 real `.dna` files.

**Why deferred.** This is a `pl-core` *type* change rippling into `pl-fileio`
(both read and write paths), `pl-index`, and `tests/corpus.rs`, and it is a
capability addition rather than a defect fix — nothing currently reports
something false. `pl-fileio` has documented the loss honestly in
`from_molecule`'s "Known gaps", including the exhibit, the frequency, and both
halves of the real fix. It should land as its own change with the corpus check
that proves it, on the independent-oracle pattern the qualifier fix established;
bundling it into a workspace-repair pass would give it less scrutiny than a
schema change deserves.

### D2. `--follow-links` is not persisted in the index

`pl index --follow-links <root>` followed by `pl library <root>` **without** the
flag deletes every linked row and re-stamps `#!complete 1`, on a perfectly
healthy filesystem. Measured by the `pl-scan` agent: `2 removed`, `#!complete 1`,
nothing wrong on disk.

**Why deferred.** The fix cannot live in `pl-scan`: either the bins must persist
the walk options in the index and reuse them, or `scan` must refuse to record
deletions when `links_skipped > 0` and the previous index was built with
`follow_links`. That is a product decision about what an index *is*, and the
second option would make every default-flag scan refuse deletions. It also
touches the index codec's directive set, which I had already bumped `ENGINE` for
on unrelated grounds this pass; layering a format change on top of that in the
same uncommitted tree would make both harder to review. `pl-scan` declined to
choose unilaterally and so do I.

### D3. `crates/pl-index/tests/scale.rs:159` is a wall-clock budget with no headroom

`assert!(ms < 1_000)` measured 861–1,184 ms across ten runs on this machine: it
straddles its own threshold. **Proven pre-existing and not a regression** — a
fresh clone at pristine `dfd6ac9` fails the same assertion at 1,124 ms and
1,111 ms, while `dfd6ac9` plus only the `pl-index` fixes passes 2/2 in that same
clone. The comment beside it cites ~335 Mbase/s, a *release*-build figure, while
the test runs unoptimised where the real cost is ~900 ms — so the comment
asserts headroom the code does not have, which is itself the house-rule defect
class.

**Why deferred.** The remedy is a judgement about the project's performance
contract — run the budget only under `--release`, raise the number, or gate on
`cfg!(debug_assertions)` — and quietly loosening a threshold is exactly how a
future real regression gets masked. Noted here so the confirm phase is not
surprised: `cargo test -p pl-index` may go red on this machine regardless of what
anyone changed.
