## 1. Fix order

### GROUP A — shipped and broken right now (do these today; all cheap)

**A1. `prototype/dna-reader.html:946,954` — every `.dna` open ends in a false "Could not read that file"**
`renderAnatomy` still uses the deleted JS parser's block shape (`b.payload.length`, `BLOCK_NAME[...]`), but `adapt()` now builds `{type,size,derived,meaning}`. The core reads the file perfectly — correct bp, features, 12 blocks — then `show()` throws a TypeError at line 946, `openFile`'s catch overwrites the summary with an error, the Download button is left disabled, and the Anatomy tab keeps the *previous* file's text (on a fresh load, the demo GenBank's "GenBank is plain text — open it in any editor", about a `.dna`). Verified on three real files.
**Fix:** `const size = b.size;` and `name: b.meaning`. `b.size` is already `Block::size_on_disk()` = `5 + payload.len()`; I measured `sum(b.size) == totalBytes` exactly, so **do not write `5 + b.size`**.
**Risk:** nil. `tools/ci.ps1` never loads this page. `prototype/check_page.js` exists but is not in the gate and calls `coreOpen()` directly, never `show()` on a `.dna` — wire it in.

**A2. `crates/pl-fileio/src/snapgene.rs:151` — 19-byte file traps the shipped wasm**
`body + len_us` is computed in `usize`, 32-bit on wasm32. A block length ≥ `0xFFFFFFFB` wraps, the `ShortBlock` guard passes, and line 170 slices `data[5..4]`. Confirmed on the real `pl_wasm.wasm` driven from node: `RuntimeError: unreachable`.
**Fix:** `if len_us > n - body` (`body <= n` is guaranteed by the `TruncatedHeader` check at line 144). Prefer the subtraction form over `checked_add` — clippy runs with `-D warnings`.
**Risk:** none. Only `rejects_a_block_that_overruns_the_file` (snapgene.rs:531) touches this and produces the identical error. Corrected impact: the instance is *not* poisoned and the browser tool does not die — it catches the trap and displays the word "unreachable" instead of the correct diagnostic.

**A3. `crates/pl-fileio/src/xml.rs:214,221,225,236,254` and `xml.rs:54` — two parser DoS/panics, fix together**
- **Char-boundary panic:** `(b[i] as char).is_whitespace()` is a Latin-1 widening, so continuation bytes `0xA0` and `0x85` read as whitespace and the scan halts mid-codepoint. `<Feature na\u{a0}me="x"/>` in a FEATURES block panics at xml.rs:224; three more variants hit 224/257. On the shipped wasm (`panic = "abort"`) this aborts the module.
- **Quadratic `unescape`:** `s[i..].find(';')` per `&` with `i += 1` → O(n²). 400 K `&` = 2.2 s, 800 K = 8.8 s, 8 MB ≈ 15 min of pegged CPU, synchronous and uncancellable in wasm. Ten of your 41 corpus `.dna` files are already over 400 KB.
**Fix:** replace all five `as char` widenings with `b[i].is_ascii_whitespace()` (XML whitespace is exactly space/tab/CR/LF, so every stop byte becomes ASCII and `i` stays on a boundary). For `unescape`, bound the search to `b[i+1 .. (i+14).min(b.len())]`. Verified: 800 K goes 8.8 s → 3.15 ms, byte-identical output on 200,000 randomized adversarial inputs, all 8 xml.rs tests pass.
**TRAP:** do **not** also "fix" `c.is_whitespace()` at xml.rs:189 — that operates on a real `char` from `char_indices()` and is already safe; ASCII-ifying it makes the element name swallow the attribute list. And keep the `rel > 12` guard where it is; the window must reach `i+13` minimum (`&#4294967295;` has rel == 12).
**Risk:** one behaviour delta on byte `0x0B` (VT), which is not legal XML and appears zero times in your corpus. Category is wrong on the second one — it's algorithmic DoS, not a panic.
**Also:** the same escaper gap exists in `xml.rs:99-112` (`escape` covers only `& < > " '`, `_ => out.push(c)`) and in the TS `esc` (see D2). Fix all three in one pass.

**A4. `bins/pl-gui/src/map.rs:42` and `:383` — a 185-byte `.dna` kills the desktop app on open**
A segment `range="1-18446744073709551615"` reaches the renderer unvalidated. Debug: `lanes()` panics `attempt to add with overflow` at `end + 1`. Release: that wraps to 0 (features silently stacked in one lane), and `arc_points` then computes `steps = usize::MAX` and panics `capacity overflow`. Verified against `target/release/polylinker.exe`: **exit 101, both profiles**.
**Fix (one change, two parts):** `end.saturating_add(1) < s` in `lanes`, and `.min(720)` on `steps` in `arc_points` (`an_arc_is_sampled_finely_enough_to_look_curved` needs ≥ 240, and in-range sweeps never exceed TAU so the cap is inert on valid files).
**TRAP:** the finding's "clamp coordinates when building `Band`s" is the wrong fix — it silently truncates (invariant 4) and it must happen *before* map.rs:92 or it misses `lanes` entirely. The real gap is that **nothing under `bins/` ever calls `Molecule::validate()`**, which already reports this exact case as `Invalid::PastEnd`. Call the validator you already have at load and surface it. Note `bins/pl-gui/src/map.rs:220` and `:441` (`span * i / 10 + 1`) have the same exposure if the file omits the SEQUENCE block — `saturating_add` in `lanes` alone does not make the panel safe.
**Risk:** none. No `map.rs` test uses coordinates over 300; `bands()` is private and untested.

### GROUP B — silent corruption of real files through shipped paths

**B1. `crates/pl-fileio/src/genbank.rs:199, 205-206, 215-216, 399` — the GenBank qualifier round trip, three defects, one fix**
These must land together; fixing any one alone makes the others harder to see.
- **`:199`** — a continuation line of an open quoted value that starts with `/` is read as a new qualifier. The value truncates, the continuation becomes a *fabricated* qualifier key with an empty value, and all further continuation lines are dropped. **168 occurrences across 66 of your 303 corpus GenBank files.** And it is self-inflicted: `qualifier_lines` wraps on spaces, so `genbank::write` → `genbank::parse` is not idempotent for any name containing " / " — I reproduced a 49-char feature name losing its tail through Polylinker alone.
- **`:206`** — `trim_matches('"')` never collapses `""` → `"`. Quote count doubles every save/load cycle (2→4→8→16, measured). A value ending in `"` loses it; a value that is just `"` becomes empty and is then deleted by the writer. Worse: when an escaped `""` lands at a wrap boundary, `ends_with('"')` reads it as a close, `open_qual` clears, and **every remaining continuation line is silently discarded**. Biopython reads your own output correctly, so the writer is right and the reader is wrong.
- **`:399`** — `v.is_empty()` skips valueless qualifiers on write. `/pseudo` (**11,561 in your corpus, 180 files**), `/ribosomal_slippage` (114), `/trans_splicing`, `/replace=""` are deleted on export. A pseudogene silently becomes a protein-coding gene.
**Fix:** replace the three `ends_with('"')` / `trim_matches` heuristics with a real quote-state machine that counts `""` as an escaped literal; treat any line as a continuation while a value is open regardless of a leading `/`; give `qualifier_lines` a bare-`/key` form. Collapse `""` **after** joining continuations and **before** `flush` derives `name` and the colour hex (genbank.rs:120-145), or names and colours will disagree.
**TRAPS:** (a) removing `v.is_empty()` starts emitting the junk keys from `:199` into real files — `/ Energy production and conversion]; Region: UbiH;` etc. Validate the key charset in the same commit. (b) `(k, "")` cannot distinguish bare `/pseudo` from `/replace=""`; a fully correct fix wants `Vec<(String, Option<String>)>` on `Feature`, which ripples into pl-core/pl-wasm/snapgene. (c) add a force-close-on-feature-flush fallback so a truncated file merges values rather than swallowing keys.
**Why the gate misses it:** `corpus.rs:186-230` compares sequence, topology, feature *count*, coordinates and colour. It never compares a feature name or a qualifier value.

**B2. `crates/pl-clone/src/lib.rs:79, 112, 132` — `Dseq` reads `ovhg` with the wrong sign in three places**
`fragment()` (line 279, `ovhg = top.0 - bot.0`), `left_end()` and `to_string_full()`'s head all place crick at `[-ovhg, -ovhg+c)`. `right_end()` and `len()` place it at `[ovhg, ovhg+c)`. Consequences, all reproduced:
- `len()` over-reports every sticky fragment by `|ovhg|` (BamHI right fragment: 9 nt reported as 13). Not `2*|ovhg|` as filed.
- `right_end()` calls a blunt fragment an 8-base 3' overhang. Re-closing the molecule you just cut returns `ligates_with == false`. PLAN.md:556 and :698 list "complete digest → religation reconstructs the original" as a validation criterion; it currently fails.
- `to_string_full()` has no term for crick's right protrusion, so a sequential double digest **deletes bases**: `cut(cut(x, BamHI)[0], EcoRI)` sums to 11 nt from a 15 nt molecule, and the GATC is not recoverable from any strand.
**Fix:** `len()` → `left = 0.min(-ovhg); right = w.max(c - ovhg)`. `right_end()` → `d = w + ovhg - c`. `to_string_full()` → append `rc(&crick[..tail_len])` where `tail_len = c - ovhg - w` when positive. Fix the wrong comment at lib.rs:78 in the same commit — it is what will send the next reader to "fix" `fragment()` instead.
**TRAPS:** (a) do **not** touch `fragment()`, `left_end()` or the stored `ovhg` — `reference/python/tests/xcheck_clone.py:74` asserts field-for-field equality with pydna and currently passes. `-ovhg` is the correct convention, fixed externally. (b) the `to_string_full` head branch must stay guarded by `ovhg > 0`; computing it unconditionally underflows on negative ovhg. (c) fixing `to_string_full` recovers the bases but not the end shapes — `cut()` re-derives from a flat string, so a second digest still treats protrusions as duplex. Log that as known, not as "sequential digests now work".
**Risk:** all 15 pl-clone tests pass unchanged; every test that touches `right_end`/`len` uses `ovhg == 0`, where both formulas agree.

**B3. `crates/pl-fileio/src/genbank.rs:57-61, 72-79, 360` — the LOCUS line, read and write**
- **Read:** topology and strandedness are decided by `contains("circular")` / `contains("ds-")` / `contains("ss-")` over the *whole* line, name included. `pCircularise` parses as circular though the field says `linear`; `pcDNA3-ss-mCherry` asserts `double_stranded: Some(false)` about an ordinary plasmid. And it is self-inflicted: `locus_name` keeps `-` and `write` puts the document title in the name column, so Polylinker's own export of a linear molecule titled `pCircularise-v2.dna` reads back circular. `Topology` has no Unknown variant, so a wrong circular flag feeds `pl_enzymes::cut_positions`/`fragments` and changes computed digest results.
- **Write:** every field sits left of spec — length ends at col 36 not 40, `bp` at 38-39 not 42-43, topology at 52-59 not 56-63, line is 75 chars not 79. Biopython 1.87 emits `BiopythonParserWarning: Attempting to parse malformed locus line` on **100% of Polylinker exports** and 0/303 real corpus files. It recovers every field via its lenient fallback, so this is conformance, not corruption — but any column-addressed reader gets `"ular SYN"` for topology. The `{:>7}` length field also overflows at ≥ 10 Mbp, reachable with zero allocation via an annotation-only molecule.
**Fix:** tokenise on read (mol-type from the token after `bp`/`aa`, skipping token index 1; topology from an exact `circular`/`linear` token). Re-column on write to land at exactly 79 chars.
**TRAPS:** (a) genbank.rs:366 emits the literal `"linear  "` with hand-padding — switching to `{:<8}` without changing that string re-shifts everything. (b) 78 chars trades one Biopython warning for another ("Truncated LOCUS line"); 79 is the target. (c) `tools/make-demo.py:104` is a second, divergent LOCUS writer that generates the checked-in `prototype/demo-construct.gb`; CI never diffs it. Fix both. (d) real corpus LOCUS lines are ragged (`LOCUS       WT       74 bp`, and one name containing `|` pipes) — positional rules must degrade to `Linear`/`None`, not guess.
**Risk:** the 344-file corpus round trip asserts topology preservation and would catch a regression; re-run it. No corpus assertion depends on GenBank `double_stranded`.

**B4. `crates/pl-fileio/src/lib.rs:100-104` — `load()` drops records and inflates lengths**
Two defects on the same four lines.
- **Multi-record:** `genbank::parse`/`fasta::parse` are `parse_all(...).next().unwrap_or_default()`, and `load` returns `(Molecule, Format)` with no channel to say more existed. `PROKKA_03062018.gbk`: 124 records, 2040 features → 161 returned, 1879 gone. `MyDocument_1.gb`: record 1 is 22 kb of bases, record 2 is the 40 annotations — user sees a bare sequence, silently. 8 of 303 corpus GenBank files and **351 multi-record FASTA** files. Worse, `pl convert` (main.rs:318 → 354) then writes the truncated molecule back, and for a `.gb` → genbank the computed destination equals the input path (`claimed` at main.rs:312 only guards output-vs-output). I reproduced an **in-place destructive overwrite**: 36,195 → 28,363 bytes, one LOCUS line, 40 annotations gone, CLI reported "0 feat / converted 1 file(s)".
- **`from_utf8_lossy`:** one invalid byte in ORIGIN becomes U+FFFD (3 bytes) and the byte-filter accepts all three as bases. A 12 bp record reads as 14 bp; every feature after that position now points at the wrong bases (verified: a feature at 5..8 returns `"aagg"` clean and `"gtaa"` corrupt), `gc_percent` shifts, and `validate()` returns `[]` because `Invalid` has no length variant. The `.dna` path is byte-preserving and unaffected.
**Fix:** (a) return the record count from `load` (or add `load_with_report`) so the caller can say "1 of 124 shown"; separately, make `pl convert` refuse to write over its input. (b) add an `Invalid` variant for `declared_len != seq.len()`, **guarded on `!seq.is_empty()`**.
**TRAPS:** (a) do **not** make multi-record a `LoadError` — `crates/pl-fileio/tests/corpus.rs:662` and `crates/pl-features/tests/corpus.rs:159,257` all use `let Ok(...) else { continue; }`, so they would silently stop checking 359 files and stay green. (b) an unguarded length check breaks the deliberate annotation-only design and fails two existing tests (genbank.rs:509, pl-core lib.rs:599). (c) adding an `Invalid` variant breaks the one exhaustive match, `crates/pl-fileio/tests/corpus.rs:672-675`. (d) strict `from_utf8` does **not** fix it — a *valid* multibyte char in ORIGIN inflates identically (measured: U+00B5 gives 13 bp against a declared 12). The root cause is the byte-filter plus the missing length check, not the encoding.
Measured: 0 of 1137 corpus text files are non-UTF-8, and 0 of 291 GenBank files with both a declared length and bases disagree — so the guarded check has zero false positives today.

**B5. `crates/pl-fileio/src/snapgene.rs:375-376` — `BindingSite` u64 overflow from a hostile `.dna`**
`location="18446744073709551615-1"` → `start + 1` panics in debug (`snapgene.rs:375:44`, exact column verified), wraps in release to `{start: 0, end: 2}`. Nothing on the file-open path calls `validate()`, so the wrapped coordinate enters the model unflagged; the GenBank writer then silently `continue`s past it (genbank.rs:413), so the primer disappears from the export.

**TRAP:** the "skip" is itself an invariant-4 silent drop, propagating an existing one at snapgene.rs:366. Do it knowingly; the honest fix needs a diagnostics channel out of `parse_primers`, which is a signature change through three call sites. Do **not** add a symmetric guard to the `Segment` path (snapgene.rs:283) — it does no arithmetic and the corpus tests pin its values.
**Risk:** none. `binding_sites_are_zero_based_unlike_segments` still passes verbatim; round-trip byte-exactness is structurally immune because `write_blocks` re-emits original payloads.

**B6. `crates/pl-features/src/index.rs:220, 234, 272-274` — nondeterministic annotation from HashMap iteration**
`Index::chain` iterates a `std::collections::HashMap` and dedups on `(record, window)`, which is not a total key over the chains `merged` can produce — two chains can share a window and differ only in `record_span`, and which survives is decided by hash order. That choice propagates to whether a feature is reported at all: on a repeat-bearing record against a short linear fragment, `annotate()` returned the feature on 57% of 3000 identical calls and nothing on 43%, same process, same bytes.
**Fix:** make `merged` a `BTreeMap` (or sort its keys, as `buckets` already does at index.rs:221-222) and widen both keys to `(record, window, record_span, diagonal, Reverse(seeds))`. Verified: all four existing chain tests produce byte-identical Chains; `chaining_is_deterministic` (index.rs:462) is currently vacuous and becomes real.
**Latency:** your shipped 8-record `features.tsv` cannot trigger it (TetA's only internal repeat puts one seed on the off-diagonal, below `min_seeds`), and 78 fragment/annotate sweeps over the real DB found zero nondeterminism. It fires the first time a repeat-bearing record (tetO7, lacO, 5xUAS, TALE, ITR) is added — which PLAN §8.3 plans for.
**Note:** returning both chains means `verify()` runs twice per collision; that is already adjudicated deterministically downstream by `dedupe`/`resolve_overlaps`.

### GROUP C — the oplog and coordinate model (zero blast radius today, "cannot be retrofitted" per ADR-2)

Nothing under `bins/`, `crates/pl-wasm/` or `ts/` references `OpLog` — there is no `undo`/`redo` string anywhere. These are latent. They become live the day undo is wired to the GUI, and content-addressing is a wire format, so **the encoding fix is free today and never again**.

**C1. `crates/pl-core/src/oplog.rs:150-164` — two different `SetFeature` edits derive the same `OpId`, and one is silently discarded**
`OpKind::content()` hashes name, kind, strand and segment start/end — not `qualifiers`, `Segment::color`, `Segment::translated` or `Segment::kind`. This violates the function's own contract at oplog.rs:116-121. Undo, then re-edit a feature changing only a qualifier: `derive_id` collides, the dedup branch skips the push, but `cursor` and `current` advance anyway (oplog.rs:505-515). `all_ops().len() == 1`. Undo+redo returns version A. `apply` returns `Ok`. Reproduced with the exact OpId prefix `3324716e`. Two further encoding defects at the same site: NUL delimiters are ambiguous (`("a\0b","c")` collides with `("a","b\0c")`), and at a `SNAPSHOT_EVERY` boundary the snapshot cache and the recorded op disagree about what one OpId means (determinism, invariant 5).
**Fix:** append qualifiers and per-segment colour/translated/kind to `content()`, with u32-BE length prefixes instead of NUL delimiters. SetFeature arm only.
**TRAP:** do **not** implement "record a distinct op" in the dedup branch — that breaks content addressing and fails `identical_work_from_an_identical_start_gets_identical_ids` (oplog.rs:772-809). Do **not** implement "assert that replaying reproduces `next`" — `Molecule` has no `PartialEq`, and an `assert!` on a path reachable from parsed file data is itself a HIGH finding.
**Risk:** zero. No test asserts a literal OpId; no oplog test constructs a `SetFeature` at all; `pl-fileio/tests/corpus.rs:548-585` asserts on checksums and coordinates, never ids. Record the encoding version in PLAN/DNA-FORMAT while you're there.

**C2. `crates/pl-core/src/oplog.rs:305-332` + `:498` — revcomp underflow, and the gate that lets it commit**
`ReverseComplement` computes `n - b + 1` with `n = mol.len()` and no bound on `b`. Debug panics at oplog.rs:312 (segments) and :324 (primer sites) on (a) an annotation-only molecule that `is_valid()` accepts — because `validate()` measures against `annotation_span()` while this arm measures against `len()` — and (b) any molecule with a broken-on-arrival coordinate, which oplog.rs:935 makes policy to permit. In release it wraps, and the corruption **commits**: the `WouldCorrupt` gate at oplog.rs:498 is `if after.len() > before.len()`, revcomp trades one `PastEnd` for one `Inverted`, 1 is not > 1, so `log.apply` returns `Ok` with `start: 18446744073709550634` in `current()`.
The gate is separately broken: any edit that swaps one pre-existing problem for a different new one is accepted (verified: a `SetFeature` introducing a fresh `PastEnd` on a dirty molecule is accepted, while the same edit on a clean molecule is correctly refused).
**Fix (revcomp):** use `mol.span()` instead of `mol.len()` as `n` — a strict generalization, since they are equal whenever `seq` is non-empty. Use saturating arithmetic for out-of-range coordinates so the *pre-existing* problem is still reported and no *new* one appears.
**TRAPS:** (a) "return `OutOfRange` when `seq.is_empty()`" makes revcomp refuse annotation-only GenBank — a silent capability regression no test catches. (b) "drop annotations that cannot be reflected" is invariant 4.
**Fix (gate) — DO NOT apply the suggested one-liner.** Deleting `if after.len() > before.len()` fixes the reported case and then refuses ordinary edits, because `Invalid` is compared by value and every variant carries data that moves under normal editing. Verified against a patched copy: a length-changing insert on a file with one `PastEnd` feature is refused; removing feature 0 is refused because `what` embeds the index; **renaming** a feature the importer broke is refused because `what` embeds the name. All 62 unit tests still pass — including `a_file_that_arrived_broken_can_still_be_edited` (oplog.rs:934), which survives only by accident (its fixture's segment is wiped by `remap_annotations`, so `after.validate()` is `[]`). That test is vacuous and needs a real fixture. A correct fix needs a **stable problem identity** that excludes molecule length and the feature index/name. File it; don't rush it.

**C3. `crates/pl-core/src/lib.rs:406-430` + `:106-112` — `rotate` and the inverted-segment contradiction**
`rotate` maps each endpoint independently through `((p - 1 + n - shift) % n) + 1` and never splits. Two failures:
- Any single-segment feature straddling the new origin comes out `end < start`. **23 of 78 rotations of 13 previously-valid real corpus plasmids leave the molecule invalid.** All 23 are refused through the oplog (`WouldCorrupt`), so "set origin" is impossible on ~30% of rotations. And on export, `genbank::format_location` emits `misc_feature 12..3`, which `genbank::parse` **silently drops** — 1 feature in, 0 out, reported valid. That round-trip loss is the worst consequence and the original finding understated it.
- `p - 1` underflows on `start == 0`, which the SnapGene parser can produce (`<Segment range="0-4"/>`; the GenBank parser checks `start > 0` at genbank.rs:275, SnapGene does not). Debug panics at lib.rs:416:41; the shipped wasm profile (overflow-checks off, `panic = "abort"`) instead silently relocates `0-4` → `12-16`. No real corpus file triggers this.
- Related: `Segment::len()` returns 1 for an inverted span while `is_empty()` returns true and the doc says 0. Zero callers workspace-wide — a self-contradictory contract, not a live miscomputation.
**The underlying defect is a contradiction, not a missing split.** `Molecule::subseq` (lib.rs:313-319), the TS renderer's `segmentRanges` (whose doc comment says an end-before-start feature "runs across the origin, and is two arcs on screen"), and `pl-features/src/annotate.rs:139` all treat `end < start` on a circular molecule as a legitimate wrap. `Invalid::Inverted` calls the same shape a mistake.
**Cheapest correct fix:** teach `validate()` that an inverted segment on a **circular** molecule is a wrap. That fixes the oplog refusal outright with none of the costs below. GenBank genuinely cannot express `12..3`, so the split belongs in `genbank::format_location` as `join(12..16,1..3)` — at the format boundary, where the 1-based/0-based conversions already live per PLAN §5.3.1. Separately, clamp `p` into `1..=n` in the remap closure, and change `Segment::len` to `if end < start { 0 } else { (end - start).saturating_add(1) }`.
**TRAPS:** (a) splitting inside `rotate()` changes a published JSON contract — `Feature::start()`/`end()` are min/max over segments, so a split feature reports `start=1, end=n` and `pl-wasm`'s `summary_json` emits an 800 bp feature as spanning the whole plasmid. It also makes rotate non-idempotent in shape. (b) `if p == 0 { return 0; }` maps `0-4` to `0-16` — it silently changes the annotation's *length*, which is worse than the shift. Clamp instead. (c) do **not** add a `start > 0` rejection to the SnapGene parser — that is a silent drop, and `corpus.rs:673,691` explicitly document `ZeroStart` as a state the importer is expected to carry and report. If anything the GenBank guard is the one that's wrong. (d) `Segment::len`'s existing `saturating_sub`/`saturating_add` is load-bearing: `end - start + 1` panics on `end == u64::MAX`, which the SnapGene parser accepts from a hostile file.
**Unmasking risk:** the corpus oplog test (corpus.rs:552-584) swallows refusals with `if log.apply(...).is_ok()`. Fixing the rotate refusal makes those applies start succeeding, running assertions at corpus.rs:591-614 over paths they have never reached. That test conceals current behaviour more than it encodes it.

**C4. `crates/pl-core/src/oplog.rs:376-397` — `ReplaceRange` re-anchors a wholly-replaced feature instead of dropping it**
`map_start`/`map_end` collapse any interior coordinate to `start` / `start + new_len - 1` whenever `new_len > 0`, so no segment is ever dropped by a replacement. A "GGGG-box" at 9..12, after `ReplaceRange{5,8,"NN"}`, survives at 5..6 annotating two Ns. Paste a 20 bp linker over AmpR plus flanks and AmpR becomes a 20 bp feature sitting on the linker. Worse, `ReplaceRange{1, n, <the same bases>}` — sequence byte-identical — moves a feature 5..12 → 1..16. This contradicts the function's own docstring at oplog.rs:363-369 ("if *nothing* survives, the segment is dropped... a one-base `AmpR` sitting in the file: valid, plausible at a glance, and false").
**TRAP — do not apply the suggested fix.** Returning `None` for every strictly-interior coordinate silently deletes the feature on the two commonest real replace operations: a 1 bp point mutation of a 1 bp feature (`snp` 9..9 + `Replace{9,1,"T"}`), and an equal-length codon-optimisation swap over exactly a feature's span. Both are currently *correct*.
**Fix:** branch on length. `new_len == old_len` → keep the current clamp (exact). `new_len != old_len` → `None` for interior, let the straddle fallbacks keep the outside.
**Risk:** `ReplaceRange` appears in exactly one test in the whole repo (oplog.rs:915), which asserts only `is_valid()` on a zero-feature molecule — it passes whether the feature survives, is mangled, or is deleted. **A wrong fix here breaks zero tests.** Land it with cases for: interior+shorter (drop), interior+longer (drop), interior+equal (preserve), 1 bp point mutation (preserve), straddle (truncate), identity replacement (unchanged). Also: `oplog.rs:401-405` contains a dead expression (`.then(|| ...).map(|_| start)` ≡ `.then_some(start)`) — safe to simplify independently.
**Reachability note:** `ReplaceRange` has no production caller anywhere.

**C5. `crates/pl-core/src/oplog.rs:575-581` — `forks()` returns HashMap iteration order**
Four builds of the identical log in the **same process** gave four distinct orders. The one caller asserts only `.len() == 0`, so it is structurally blind. Zero production consumers today; the immediate cost is that any test or golden file pinning fork order will flake.
**Fix:** key by the op's index in `self.ops` via `by_id` — that gives creation order, which is what a history panel wants, rather than SHA-1 byte order. Do **not** reorder the `children` *values*; `redo()` reads `.last()` for its documented "most recent branch" semantics.

**D1. `packages/circular-map/src/render.ts:72` + `geometry.ts:220-222` — a GenBank feature key on `Object.prototype` crashes the render**

**D2. `packages/circular-map/src/geometry.ts:192-199` — `esc()` lets XML-illegal control characters through**

**D3. `packages/circular-map/src/render.ts:134, 209, 301` + `geometry.ts:67-69` — unvalidated numbers reach the geometry; three symptoms, one fix**
- `length = Math.max(1, Math.floor(molecule.length))` doesn't guard `Infinity`. `niceStep(Infinity/12)` returns 1, so the ruler loop is `for (base = 1; base <= Infinity; base += 1)` pushing two strings per iteration. - A label whose position computes to `NaN` is neither drawn, nor in `labels`, nor in `hiddenLabels` — the invariant `labels.length + hiddenLabels.length === anchors` (which `render.test.ts:85` asserts for the crowded case) breaks. `hiddenLabels` is the *only* documented signal that a map is incomplete, and it says everything is fine.

Also don't overload `hiddenLabels`, whose docstring promises "could not be placed without overlapping" and tells the caller to enlarge the canvas — advice that cannot work for a NaN.
**Note:** `segmentRanges` is a public export; changing its return is semver-visible. Prefer doing the detection in `renderCircularMap`.

**D4. `packages/circular-map/src/labels.ts:131` — `placeColumn` clamps the regression *input*, so placement is not optimal**
The box constraint is applied to the targets before PAVA, which changes the weighted block means. Six identical labels wanting y=50 come back centred on 53.333 instead of 50, every one 3.33 px low in the same direction, when the optimum `[20,32,...,80]` is plainly feasible. **Fix:** unclamped targets, clamp the isotonic *output*. I verified against a Dykstra alternating-projection solver over 19,174 columns: max cost difference 9.1e-13, i.e. the clamp-on-output is the exact constrained optimum (constant bounds ⇒ the clamp is the exact projection onto the intersection). Feasibility and non-overlap hold on all 19,174.
**Must do in the same commit:** rewrite the comment at labels.ts:115-118, which currently explains *why the clamp is on the input*. Leaving it invites a future "restore". The existing optimality test only compares against randomly generated loose stacks and can never find the tighter answer — replace it with a symmetry assertion (n identical boxes ⇒ stack centred on the shared ideal, which fails at n=5 and passes at n=3, exactly why this survived).
**Note:** the derivation the comment claims *is* correct — `zLo`/`zHi` really are index-independent, the per-height terms cancel. Only the clamp order is wrong. The loop at labels.ts:123-129 is a no-op.

**D5. `packages/circular-map/src/geometry.ts:113` — `arcPath` draws a zero-length span as a full annulus**
`{from:400, to:400}` on a 1000 bp molecule returns a complete 18 px ring. The comment says the case is disambiguated "using the base range that produced them"; the code never inspects `spec.from`/`spec.to`. Only the *replacement* case is broken (C4).

**Snapshot replay is correct.** 120 ops across two `SNAPSHOT_EVERY` boundaries, seek back to all 120 cursors: 0 of 120 diverged. Replay-from-snapshot equals replay-from-zero.

**`Dseq` chemistry and the 50-enzyme table are correct.** All 50 recognition sites verified as true palindromes (so top-strand-only scanning is sound) and all 50 cut offsets verified against REBASE. `left_end()` reads `ovhg` with the right sign. `End::ligates_with` is symmetric and correct. `cut()` fragment counts, order, tiling and circular-origin handling match pydna, including rotation invariance — which is exactly why the pydna differential passes while the derived accessors (B2) are wrong.

**No memory-safety or ABI defect in `pl-wasm`.** `pl_alloc`/`pl_free` match exactly (`Vec::with_capacity` + `mem::forget` / `from_raw_parts(ptr, 0, len)`); the `pl_alloc(0)` dangling pointer is handled; every `set_out` call site drops its `RefCell` borrow first (checked individually across all seven), so no double-borrow panic; `read_str` guards null and zero length. The two obvious ABI traps are already defended downstream (`width=0` → `line_width.max(1)`; `month >= 12` → `MONTHS[m.min(11)]`). No attacker-controlled `Vec::with_capacity` anywhere in the binary parsers — there is no heap-exhaustion primitive in `read_blocks`. Both JSON escapers are correct.

**Framing and XML structure in the `.dna` parser are robust.** Empty/1/4/5-byte files, `len=0x7FFFFFFF`, trailing partial blocks, 13-byte headers, zero-length SEQUENCE payloads, 100,000 zero-length blocks, a nested `.dna` in a payload — all return the right `Err` or parse cleanly. No recursion in the XML scanner (200,000 nested tags fine); no entity-expansion amplification; every entity edge case (`&#99999999999;`, `&#xD800;`, `&#0;`, bare `&`) handled. Every slice in `snapgene.rs`/`xml.rs`/`lib.rs` is bounds-safe except the three reported.

**No panic reachable from the annotator.** 6,000 `annotate()` calls over hostile alphabets with randomized `Config`, plus 1,500 planted-and-damaged rounds on both strands with random rotations, debug build with overflow checks: zero panics, every coordinate in `1..=len`. `walk()` cannot overrun (it's a `zip`); `tstart -= add` cannot underflow.

**No panic in `pl-gui` beyond the two reported.** All four `.expect("checked by caller")` are guarded by the same closure's early return. `total - uniq - multi` cannot underflow (the three sets are provably disjoint). Every division has a `.max(1)` guard. `b.segs[0]` is safe because `bands()` pushes a fallback.

**Determinism holds everywhere except the two HashMap sites.** `genbank.rs`, `fasta.rs`, `map.rs` and the primitives contain no HashMap, no time, no randomness. Feature order is file order by design. `resolve_overlaps`' comparator is total (`score` can never be NaN — `aligned >= 1` and `db_units == 0` is rejected), and `sort_by` is stable. The `placeColumn` drop loop is input-order-independent (strict `<` plus stable sort).

**Zero-external-dependency invariant holds.** `pl-core` has an empty `[dependencies]`; `pl-features` depends only on `pl-core`; `pl-fileio` only on `pl-core`; `pl-clone` only on `pl-core` + `pl-enzymes`; `packages/circular-map` has one devDependency (`typescript`) and one non-relative import in the whole package (`node:fs`, in an example).

**SVG colour injection is closed.** `safeColor` covers `f.color`, the type-derived colour and all eight theme colours. I tried `url(#g)`, embedded newlines, whitespace padding and over-long keywords — nothing escapes the attribute. `id` → `data-feature-id` and `note` → `<title>` are both escaped. Ordinary output validates as XML.

**`build.py` translation and determinism are sound.** The codon indexing is right and all 8 markers' CDS translate to an exact AMRProt match. The selection is byte-for-byte reproducible on the current release (no ties in the sort key for any marker; stable sort over fixed FASTA order). The fetch retry loop cannot corrupt the cache on a network error — it fails loudly before any write.

## 6. Themes

**1. The gate tests the *shape* of the answer, never its *content*.** This is the single highest-leverage thing to change. `corpus.rs:186-230` compares sequence, topology, feature *count*, coordinates and colour — so B1 (qualifier corruption at 168 sites), B3 (strandedness), and the `Strand::Unoriented` flattening all pass through 344 real files invisibly. `corpus.rs:191-198` bounds a reported length by the *record*, not the molecule, so a 750 bp call on a 500 bp plasmid passes. `corpus.rs:429-470` explicitly rotates "including ones that land mid-feature" and then checks only `features.len()` and `f.end() > n` — neither of which can see an inverted segment. Adding one assertion — `write` then `parse` must reproduce every feature name and every qualifier pair — would have caught four HIGH findings at once.

**2. Green tests that pass by construction.** Six tests in this codebase cannot fail: `chaining_is_deterministic` (its feature is non-repetitive, so no two buckets ever share a window); `adjacent_features_are_both_kept` (passes with the trim set to zero); `two_features_at_the_same_place_do_not_both_survive` (asserts `len() <= 2` and emits 2); `a_file_that_arrived_broken_can_still_be_edited` (its fixture's segment is wiped by the remap, so `validate()` is empty); `the placement is optimal, not merely feasible` (compares only against random loose stacks that never find the tighter answer); `locus_line_keeps_its_columns_even_with_a_long_name` (checks only the name column). Two more actively *hide* failures with `if ... .is_ok()` and `else { continue }`. These are worse than no test — they signal coverage that does not exist. Audit them as a batch.

**3. `Option` is modelled correctly and then unwrapped at the boundary.** The core is scrupulous about unknown-as-a-real-state — `declared_len: Option<u64>`, `double_stranded: Option<bool>`, `Strand::Unoriented` with a doc comment explaining that the loss should be visible where it happens, `Composition::gc_percent` returning `Option`. Then `main.rs:216` does `unwrap_or(0)`, `genbank.rs:322` tests only `is_reverse()`, `build.py:337` does `.get("sha256", "")`, and `render.ts:134` does `Math.max(1, ...)`. Every one of those turns "we don't know" into a positive claim. The pattern to copy is `pl-wasm`'s `summary_json`, which emits `null`.

**4. `validate()` exists, is correct, and is never called on the path that needs it.** `Molecule::validate` already reports `PastEnd`, `ZeroStart`, `Inverted` and `FeatureWithoutSegments` — it would have caught A4, B5 and half of C3 at load. But nothing under `bins/` references it, `pl_open` doesn't call it, and `OpLog::apply` compares it with a broken count gate. The parsers are not too permissive; the callers just never ask.

**5. Silent *fabrication*, not just silent loss.** Invariant 4 says "never silently drop", and the codebase mostly honours it. The worse pattern here is inventing data: `bond(5,10)` → a `10..10` segment that `validate()` accepts; a truncated GenBank → a labelled phantom feature at 12 o'clock; a wrapped `/note` continuation → a fabricated qualifier key; a truncated download → a *different nucleotide sequence* under the same feature name; a wholly-replaced AmpR → a 20 bp AmpR sitting on a linker. Dropping is at least detectable by counting. Consider stating fabrication as its own invariant.

**6. HashMap iteration order.** Twice, in two languages' worth of separation (`OpLog::forks`, `Index::chain`). Both times, adjacent code in the same function already sorts a different collection for exactly this reason. A lint (`clippy::iter_over_hash_type`) would close the class.

**7. The `-ovhg` / `+ovhg` sign, and 0-vs-1-based, are still the #1 bug source — and the tell is always a stale comment.** `lib.rs:78` says crick occupies `[ovhg, ovhg+c)`; it doesn't. `oplog.rs:111-112` says a full-circle and a zero-length feature are disambiguated by the base range; they aren't. `labels.ts:115-118` explains why the clamp is on the input; it shouldn't be. `translate.rs:18` cites a cross-check file that doesn't exist. `align.rs:121` justifies a reset with a scenario that cannot occur. `seguid.rs:88` links a method never written. In every case the comment states the *correct* intent and the code does something else — which means the comments are a reliable oracle for finding the next one. Grep them.

**Overall:** the correctness core — checksums, translation tables, the aligner, circular coordinate mapping, enzyme chemistry, memory safety — is genuinely in good shape and verified against external references at a level most projects never reach. Every defect found is at a boundary: parser-to-model, model-to-writer, or library-to-caller. That is a good place for the bugs to be, and it is why most of these fixes are small.
