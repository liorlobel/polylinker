## Verdict

This codebase is sound. Two findings below produce a coordinate a biologist
would act on, and they are NOT the same shape — an earlier draft of this
paragraph said they were, and that was wrong. **#1** is an origin-crossing
feature whose span is recomputed by code that recognises one spelling of the
wrap and not the one an ordinary rotation produces. **#2** is a mirror taken
about the wrong length, so a feature on a flipped fragment lands `|ovhg|` bases
off — four, for every common six-cutter, and nothing to do with the origin.
They share only their consequence. Everything else is a hedge lost at a
boundary, a count that is wrong on screen while the underlying value is right,
or a test whose name claims a distinction its body never draws.

**Both were reproduced by execution before this document was written**, which
matters because the sweep that found them did not run code. The probes and
their output are recorded under each finding; both were then removed and the
tree left byte-identical to `f0e4a6f`.

The distribution is diagnostic and worth stating plainly: **9 of 19 findings are
in `bins/pl-gui`, and all 66,000 lines of `crates/` yielded 5, three of them
low.** That is not an artefact of effort. Sort the tree by whether an executable
oracle exists for it — digest and cloning against pydna, Tm and translation and
SEGUID and motif search and primer binding against Biopython, EPS and PNG
against resvg and zlib — and the crates with oracles produced almost nothing,
while the panels that assemble those correct values into what a user reads
produced nearly everything. The science core is in good shape. The layer between
it and the user is where the remaining defects are, and it is the layer with no
oracle and the weakest tests.

The four "check that cannot fail" findings (#11–#15) are the ones I would act on
first regardless of severity, because this project has written house rule 1 into
its own documents and each of these is a place where the rule is currently not
being kept.

### 1. `crates/pl-core/src/lib.rs:225` — wrong-answer — HIGH

`Feature::extent` recognises an origin crossing only in the one *spelling*
`genbank::write` emits: a multi-part join whose last segment starts at base 1
and whose penultimate segment ends at the molecule length (`if circular && span
> 0 && last.start == 1 && last.end < first.start`, then `if prev.end == span`).
`Molecule::rotate` (lib.rs:815-827) remaps every endpoint in place and never
re-splits, re-orders or re-normalises the segments, so rotating a molecule that
carries such a join moves the crossing into a segment that is no longer
last-and-starting-at-1. The guard fails and `extent` falls back to
`(self.start(), self.end())` — a min over segment starts and a max over segment
ends — which for that shape returns a pair that does not contain the feature.
The doc comment two lines above (lib.rs:210-212) says the fallback "is an outer
bound: the pair covers the intervening bases the segments do not". For the shape
`rotate` produces it is an *inner* subset, which is the opposite failure.

Nothing normalises afterwards. `oplog::apply`'s `Rotate` arm
(crates/pl-core/src/oplog.rs:420-431) calls `mol.rotate` and returns; a grep for
`normali[sz]e|coalesce|merge_wrap` over `crates/` and `bins/` finds only
`featedit::Panel::normalise`, a GUI form on a different path. And the op-log gate
cannot refuse it: `validate()` declares `end < start` legal on a circle
(lib.rs:628), so the post-rotate shape produces zero new `Invalid`s and
`refuse_new_problems` commits.

*Failure scenario.* 400 bp circular plasmid, CDS spelled `join(381..400,1..40)` —
60 bp / 20 aa, and precisely the form `genbank::write` emits and `genbank::parse`
reads back for every wrapped feature, so any save-and-reopen produces it. The
user presses "Set origin at selected feature" on a feature at base 2
(bins/pl-gui/src/main.rs:6418-6421), or deletes a selection crossing the origin
(seqedit.rs:1275 issues `Rotate` as the first of its two ops). `rotate(2)` gives
segments `[(380,399),(400,39)]`; `extent(400,true)` returns `(380,399)`. The
Features panel row (main.rs:7903) prints "380..399"; `feature_tip`
(main.rs:15071-15100) prints "CDS · 380..399 · 20 bp (20 aa)" — 20 bases claimed
for a 20-residue protein on one line, because the "(20 aa)" comes from
`feature_bp`, which sums the segments correctly and gets 60. Clicking the feature
routes through `select_feature_span` (main.rs:13609) and selects bases 380..399,
so Ctrl+Shift+R copies 20 of the CDS's 60 bases and the design panel is handed
that 20 bp region as the amplification target. `rotate(390)` on the same feature
gives `[(392,11),(12,51)]` and extent `(12,51)`: the reported **start** is now
wrong by 380 bases, and "Set origin at selected feature" then issues `Rotate {
origin: 12 }`, renumbering the plasmid to a base 380 away from the feature it
names. `rotate(200)` on the same feature is correct (182..241) — so the answer
depends on where the molecule happens to be numbered, which is the property this
codebase repeatedly states must never hold. The map is unaffected
(`pl_draw::ranges` splits per segment and draws all 60 bases), so the picture and
the coordinate readout disagree.

*It gets worse on save.* The broken shape does not stay in memory.
`location_parts` (crates/pl-fileio/src/genbank.rs:720-743) writes a wrapping
segment as two parts, so after `rotate(390)` the feature saves as
`join(392..400,1..11,12..51)`; re-parsed that is three segments, `last.start ==
12`, the guard fails again, and `extent` returns **(1, 400)** — a 60 bp CDS
reported as the entire plasmid. That is verbatim the symptom
`docs/AUDIT-2026-07-29.md:160-179` quotes as defect #4-7 and declares fixed
("`pl info --json` reported a 17 bp promoter as `"start": 1, "end": 2686`"). The
fix recognised one spelling; `rotate` manufactures a second, and the fix does not
hold at HEAD. `bins/pl/src/main.rs:868` then serves that pair out of the saved
file with no rotate verb involved, as does `crates/pl-wasm/src/lib.rs:285`.

*Why the tests miss it.* `extent_reads_an_origin_crossing_join_as_the_wrap_it_is`
(lib.rs:1290) is the only `extent` test; every fixture in it is single-segment,
the canonical join, or a multi-segment feature with no wrapping segment.
`rotation_that_crosses_the_origin_stays_consistent` (lib.rs:1153) *does* compose
the two — `[(15,16),(1,2)]` on a 16 bp circle, `rotate(5)` — but origin 5 lands
outside the feature, which is exactly the benign case where the two segments come
out contiguous and non-wrapping, and it asserts only the four coordinates and
never calls `extent`. Changing that test's origin from 5 to 16 and adding an
`extent` assertion would fail today. The general rule, which no test states: the
fallback is correct whenever the new origin lands *outside* the wrapped feature,
and wrong exactly when the feature still crosses the origin after the rotation.

*Fix.* Recognise the crossing structurally rather than by spelling: on a circular
molecule a segment with `end < start` **is** the crossing, wherever it sits in
the list. With `i` the index of that segment, the extent is `(segments[i].start,
segments[(i + len - 1) % len].end)` — the wrapping segment's start and the end of
the segment that cyclically precedes it in file order — keeping the existing
canonical-join branch for the spelling that has no `end < start` segment. Two
such segments on one feature is not representable and should keep the min/max
fallback. Correct the "outer bound" sentence at lib.rs:210-212 in the same
commit. The regression test nobody wrote is the composition: build
`join(381..400,1..40)` on a 400 bp circle, `rotate(2)` and `rotate(390)`, and
assert `extent` still names the same 60 bases and the same start base as before.

**Reproduced by execution**, not inferred. A probe inserted into `pl-core`'s test
module built a 2,686 bp circle carrying a 17 bp feature in exactly the spelling
`genbank::write` emits, rotated it so the feature still crossed the origin, and
printed `extent` on both sides:

```
before rotate:      segments=[(2677,2686),(1,7)]  extent=(2677,7)   -> 17 bp
after rotate(2680): segments=[(2684,7),(8,14)]    extent=(8,14)     ->  7 bp
```

`rotate` turned the canonical join into one whose **first** segment wraps —
`(2684,7)` — a shape the recogniser does not test for, because it only asks
about `last`. Ten of the seventeen bases are gone and the survivor sits at the
wrong coordinates. The probe was removed; the tree is byte-identical to
`f0e4a6f`.

### 2. `bins/pl-gui/src/clone.rs:1522` — wrong-answer — HIGH

When a fragment is laid into a product **flipped**, the bases that go into the
product are `flip(frag).watson`, which is `frag.crick` — and `crick` is
`rc(full[b0..b1])`, a window offset from `watson`'s `full[t0..t1]` by the
enzyme's overhang (crates/pl-clone/src/lib.rs:588-599, `bot = top +
overhang_of(enzyme)`). `build` maps a parent coordinate into the flipped slot
with `(flen - 1 - b, flen - 1 - a)` where `flen = frags[*idx].watson.len()`
(clone.rs:1495). Deriving it properly: `crick[j] = comp(full[b1-1-j])`, `b1 = t0
- ovhg + c`, so with `a = p - t0` the correct index is `j = c - 1 - ovhg - a`,
not `w - 1 - a`. The two agree only when `ovhg == c - w`. For the ordinary
restriction fragment — same 5' overhang at both ends, so `c == w` and `ovhg ==
-k` — the code's index is `k` too small: **every carried feature is placed `k`
bases to the 5' side of where its bases really are**, `k = 4` for EcoRI, BamHI,
BglII, HindIII, XhoI, SalI, NheI, SpeI, XbaI and every other 4-base-5'-overhang
cutter. `ovhg` is never consulted anywhere in the loop.

The `(idx, true)` arm is not exotic. `Enzyme::ligates_with`
(crates/pl-clone/src/lib.rs:198-213) is `a == b && *x == rc(y)`; a fragment with
5'-AATT at both ends has `rc("AATT") == "AATT"` and so seals in either
orientation, and `walk` (ligate.rs:326-345) tries `flipped` in `&[false, true]`
for every non-pinned fragment. This is the everyday non-directional ligation.

*Failure scenario.* A plasmid with two sites for one enzyme. `pl_clone::ligate`
correctly enumerates both circular products — insert forward and insert inverted
— and the panel lists both. Click Open on the inverted one and every feature
carried off the inverted fragment is 4 bp out. Traced on the minimal case:
circular parent `GAATTCAAACCGAATTCTTTT` (n = 21), EcoRI. `digest` gives f0
`{watson "AATTCAAACCG", crick "AATTCGGTTTG", ovhg −4}` and f1 `{watson
"AATTCTTTTG", crick "AATTCAAAAG", ovhg −4}`. Both circular products form and are
distinct sequences, so `Product::identity` cannot dedup one away. Product watson
for order `[(0,false),(1,true)]` is `AATTCAAACCGAATTCAAAAG`. A feature at parent
1-based 17..19 (`CTT`) is inside f1 (`from = (13,22)`), so `a = 4`, `b = 6`, and
line 1522 gives `(3,5)` → `Segment::new(15,17)` = product bases `TCA`. The bases
the feature actually names are at product 19..21 = `AAG` = rc(`CTT`). On a real 3
kb vector that is a marker, promoter or CDS annotated four bases off in a
construct the user opens (clone.rs:622-676 lists every product with an Open
button; main.rs:14043-14075 runs it through `genbank::write_reporting` and opens
it as a saveable document), saves to GenBank, and orders primers against. A 4 bp
shift on a CDS is a frame shift in what the map draws and what the exported file
claims.

The comment at clone.rs:1493-1494 states the wrong thing in the present tense —
"Watson length, matching what locate measured and what join concatenates" —
which is true for the unflipped case and false for the flipped one, since `join`
concatenates `flip(f).watson`, i.e. `f.crick`. (That same comment also carries a
literal PowerShell `` `n `` escape mid-sentence, unrendered; cosmetic, but it is
how you can tell the line was written through a heredoc and never re-read.)

A secondary, weaker claim: `at += flen` at clone.rs:1541 is also wrong whenever a
flipped fragment has `crick.len() != watson.len()`, which happens as soon as a
digest mixes end geometries, and there the whole tail of the product's features
shifts too. I could not construct a concrete digest in which such a fragment both
flips and seals, so treat that half as unproven while the primary defect is
confirmed.

*Why the tests miss it.* No test in the crate asserts a coordinate for a `(idx,
true)` entry of `order`. `a_single_cut_religates_to_the_same_length_and_keeps_its_features`
(clone.rs:1618) has one fragment, which `ligate` pins unflipped
(ligate.rs:388-391).
`a_gene_from_one_plasmid_goes_into_a_vector_from_another_with_both_names`
(clone.rs:1668) is directional EcoRI/BamHI subcloning: each fragment has one AATT
end and one GATC end, so only the unflipped arrangement seals and its
read-the-bases-back loop exercises only the `else` arm of line 1521.
`a_feature_cut_in_half_is_dropped_and_counted` (clone.rs:2314) asserts `carried
== 0`. The two-BamHI-site fixture in main.rs:26208 *does* produce flipped
products, but it carries no features and compares sequences only.

*Fix.* Carry the fragment's geometry into `build`: for a flipped entry the slot
length is `frags[*idx].crick.len()` (use it for `at +=` as well) and the index is
`(c - 1 - ovhg - b, c - 1 - ovhg - a)`. Pin it with a test that ligates a
two-fragment single-enzyme digest, finds the inverted product, and reads the
carried feature's bases back off `prod.mol.seq` against the reverse complement of
the parent's — the same read-back oracle clone.rs:1668 already uses, applied to
the flipped product.

**Reproduced by execution.** A probe inserted into `clone.rs`'s test module cut a
donor at two EcoRI sites — giving a middle piece with an `AATT` end at each end,
which is the ordinary non-directional subcloning that lets a fragment go in
either orientation — put a 12 bp feature deliberately off-centre inside it, and
read the carried feature back off the product's own bases:

```
parent gfp bases   fwd=CCTTTAAAGGGC   rev=GCCCTTTAAAGG
order=[(0,false),(1,false)]  span=54..65  got=CCTTTAAAGGGC  OK
order=[(0,false),(1,true)]   span=65..76  got=AAGGGCCCTTTA  MISPLACED
```

`AAGGGCCCTTTA` is `GCCCTTTAAAGG` rotated by four — precisely EcoRI's four-base
5' overhang. The unflipped placement is correct, which is why the existing test
at `clone.rs:1668` passes: it asserts this same read-back invariant, but no test
anywhere in the file exercises a flipped fragment (`grep flipped` past the test
module returns nothing). The probe was removed; the tree is byte-identical to
`f0e4a6f`.

### 3. `bins/pl-gui/src/clone.rs:1509` — data-loss — MEDIUM

`locate` (clone.rs:820-846) searches a circular parent as `parent+parent` — its
own doc at :806-807 says the doubling exists so an origin-crossing fragment is
found as one run — and returns `(s+1, s+len)` at line 845 with **no `%
parent.len()`**. A fragment that crosses the origin therefore comes back with `fe
> n`. `within(f, fs, fe)` (clone.rs:1559) requires `s.start >= fs`, which no
feature in the wrapped tail (parent bases 1..fe−n) can satisfy even though those
bases are physically inside that fragment. Such a feature is counted as `dropped`
and never carried, and the offset arithmetic at 1519-1520 (`s.start - fs`) has no
modular form that could place it if it survived. `within` also requires `s.start
<= s.end`, so a feature that itself crosses the origin never travels into any
product. Both contradict the module doc at clone.rs:15-16 ("a feature travels
only when its whole span sits inside one identified fragment").

*Failure scenario.* Cut a plasmid once with a unique enzyme and religate it — the
panel's headline operation. The single fragment's watson starts at the cut, so
`from = (cut+1, cut+n)`. Every feature annotated between base 1 and the cut fails
`within` and is left out of a product that is otherwise base-for-base the plasmid
you started with. On the shipped fixture
`AAAAGGATCCTTTTGCGCGCATATATCCCGGGAAAATTTTCCCC` (44 bp) cut with BamHI the
fragment is `from = (6, 49)`; a feature at 1..4 is inside it (it lands at product
40..43) and is reported as dropped. On a real vector cut in the MCS that is every
feature upstream of the MCS, and the same happens to the backbone fragment of any
two-site digest whose backbone spans the origin, which is the usual case unless
base 1 coincides with a cut.

Two corrections to how this reads. It is **not silent** — clone.rs:641-655 prints
"{carried} feature(s) carried, {dropped} dropped" in the warning colour. What is
false is the *reason*: the hover at clone.rs:657-661 attributes every drop to
being cut in half or to an ambiguous fragment, and neither applies here. And the
more actionable half is one the report of this finding undersold: the
out-of-range interval is **rendered to the user as a coordinate**, at
clone.rs:554 in the fragment list ("from 6..49" for a 44 bp molecule) and at
clone.rs:1254 inside the Copy-record methods text ("The construct was assembled
from 1201..5400 (4,200 bp)" on a 5,000 bp plasmid) — a position that does not
exist in the parent, presented as fact in text written to be pasted into a
methods section.

*Why the tests miss it.* `a_single_cut_religates_...` (clone.rs:1618) is the test
for exactly this operation, and its only feature is at 15..30, downstream of the
BamHI cut at base 6. clone.rs:1668's vector is 60 bp with nicks at 1 and 27, so
the backbone is (28,61) whose wrapped tail is the single base 1, while `bla` sits
at 36..55 in the non-wrapped part. clone.rs:2314 and clone.rs:1953 both place
their features after the first cut. The three `locate` assertions at
clone.rs:2373-2379 all pass `circular = false`. No test puts a feature before the
first cut on a circle.

*Fix.* Make the fragment interval modular: keep `n` alongside `from`, accept a
feature when every segment satisfies `(s.start + n - fs) % n + (s.end - s.start)
< flen`, and compute the offset with the same modular expression. Fold `fe` back
into `1..=n` before it reaches the fragment list and the methods paragraph. Add a
second feature entirely before the cut to `a_single_cut_religates_...` and assert
its bases read back off `prod.mol.seq`.

### 4. `bins/pl-gui/src/main.rs:12819` — wrong-answer — MEDIUM

`Molecule::methylation` has exactly one non-test writer in the workspace —
`crates/pl-fileio/src/snapgene.rs:382`, the `.dna` flag byte. GenBank and FASTA
readers never touch it, and `Methylation` is four plain `bool`s with a derived
`Default` (crates/pl-core/src/lib.rs:363), so every molecule from those formats
carries `{dam:false, dcm:false, ecoki:false, cpg:false}` with no third state.
`pl_enzymes::methylation::site_effect` skips every rule whose methylase is not
`active_in(meth)` (crates/pl-enzymes/src/methylation.rs:395), so it returns
`None` for every site and `DigestState::verdict` is `None` for every enzyme. The
File tab then omits the methylation row **entirely** when nothing is set (`if
!meth.is_empty()`), so "this file records no methylation" and "this preparation
is unmethylated" render identically — as nothing. The row twelve lines above does
the opposite for the neighbouring `Option` field: `None => row("strands", "not
recorded".into())` (main.rs:12788), and main.rs:12083 even prints "strands are
not recorded in this file; drawn double". The honest pattern exists in the same
function and was not applied. `cpg` is not in the array at all.
`OpKind::SetMethylation` exists in pl-core but has no constructor anywhere in
`bins/` (its only occurrence outside oplog.rs is a match arm at doc.rs:989), so
there is no way to declare a dam+ or dam− prep.

*Failure scenario.* Open pKoV as `pKoV.dna`: the Enzymes tab strikes BclI through
(main.rs:15606), shows a chip and hover (15617-15628), `gel.rs:579-592` excludes
it from lane seeding, and `gel.rs:281-322` writes the caveat into the disclosure
strip and into the exported picture. Open the identical 8,117 bp as `pKoV.gb` or
`pKoV.fa` — an Addgene download, or anything exported from another tool — and
BclI is a clean unique cutter with no strike, no chip, and no methylation row
anywhere in the File tab. Tick it, and `gel::View` seeds a BclI lane and draws
predicted band sizes for a digest that will not happen in any Dam+ prep, in a
figure gel.rs:533 itself calls "a figure somebody will put in a thesis". The
entire tier-1 hazard machinery is silently absent for the dominant sharing
format. `bins/pl/src/main.rs:186-187` calls dam+ dcm+ "an ordinary lab strain",
`bins/pl/src/main.rs:5069-5076` describes this exact failure as costing a week,
and `docs/PLAN.md:733` ranks methylation-blocked sites tier 1: "never display a
digest without stating what is filtered out."

Two claims in the original report do not survive and should not be repeated: the
CLI does **not** contradict the GUI (`pl digest` applies no methylation for any
format including `.dna`, so it is uniformly blind rather than inconsistent), and
`pl design` is a different binary.

*Why the tests miss it.* `bins/pl-gui/src/doc.rs:1551-1659` and
`gel.rs:951-1020` both mutate their fixtures into Dam+ `.dna` molecules
(`dam_positive()` at gel.rs:951-957) — which is precisely why they cannot see the
default. `file_tab` (main.rs:12767) has no test at all. No test anywhere loads
one sequence through two readers and compares the enzyme verdicts.

*Fix.* Two independent halves. (a) Always render the row: `methylation — not
recorded in this file (treated as unmethylated)` when the format cannot carry it,
`none` when a `.dna` says none. The `"strands"` row twelve lines earlier is the
pattern, and the code for it is already there. (b) Wire `OpKind::SetMethylation`
to a control, which is the only way a GenBank plasmid can ever get a true
verdict. Until (b), the Enzymes tab and the gel should carry the same "dam+ dcm+
assumed / not recorded" sentence `pl design` already prints. This is the
methylation half of `UX-REVIEW-2026-07-31.md` finding 5, unchanged; the source
itself refers to it as still open at map.rs:347-349 and main.rs:13255-13260.

### 5. `bins/pl-mcp/src/main.rs:796` — wrong-answer — MEDIUM

`pl_features::annotate::Annotation` documents `wraps_origin` as "Runs across the
origin of a circular molecule, so `start > end`"
(crates/pl-features/src/annotate.rs:319-320) and debug-asserts that invariant at
annotate.rs:1069-1074. `pl annotate` renders it: `bins/pl/src/main.rs:4116`
appends "  crosses origin" and :4114 appends "  via protein". The MCP tool's
format string is `"{}..{} {} {} — {:.1}% identity, {:.0}% coverage{}"` with the
last slot filled only by `if f.is_fragment { ", fragment" }`; `wraps_origin`,
`via_protein` and `fusion_orf` are read nowhere in the crate (I ran the grep).
The result crossing the process boundary is a reversed range with nothing to
explain it.

Worse than the class alone: `bins/pl/src/main.rs:4074-4082` prints a header line
`"{path}  {n} bp circular|linear"` above the hits, so the terminal reader gets
molecule length *and* topology. The MCP reply's only preamble is
`first_record_only(&report)` (:462-471), which is empty unless the file held
multiple records. The assistant receives `681..80` with no length, no topology
and no note, and cannot reconstruct the wrap even by arithmetic.

This contradicts the crate's own header at pl-mcp/src/main.rs:13-19 — "The
results carry the same caveats the CLI prints. … An assistant will repeat
whatever it is handed, so anything hedged in the terminal has to be hedged here
too, or the hedge is lost exactly where it matters most." The same file's
`open_reading_frames` tool goes to considerable trouble to emit " (crosses
origin)" and a laps sentence (main.rs:684-694) for exactly this reason;
`annotate` was not given the same treatment.

*Failure scenario.* Open a plasmid whose AmpR — or any of the 89 shipped signed
records, and `features.tsv`'s first rows are full-length AmpR, KanR, TetA, CmR —
straddles base 1, which is routine because the numbering origin of an assembled
plasmid is wherever the assembler cut the circle.

### 9. `crates/pl-clone/src/lib.rs:716` — panic — MEDIUM

`Dseq::to_string_full` ends with `out.push_str(&rc(&self.crick[..tail as
usize]))` (lib.rs:174) where `tail = (c - ovhg - w).min(c)` is a byte count
derived from the difference in byte length between the two strands. `crick` is a
`String`, so `crick[..tail]` is a UTF-8 slice and panics unless `tail` lands on a
char boundary. For any `Dseq::new(seq, _)` whose `seq` holds a non-ASCII
character, `pl_core::reverse_complement` passes unknown bytes through **reversed**
(iupac.rs:54, :60-62), the reversed pair is not valid UTF-8, `rc()`'s
`from_utf8_lossy` (lib.rs:48-50) turns each byte into a 3-byte U+FFFD, and `crick`
ends up 4 bytes longer than `watson` with the replacement characters at its
front. `tail` is then 4, and byte 4 of `crick` is the middle of the second
U+FFFD.

The crate already knows this. `try_cut` checks `watson`/`crick` for ASCII
**before** calling `to_string_full`, and its comment says why: "The strands are
checked rather than `to_string_full()` because that method is where the phantom
bases are appended" (lib.rs:363-375). `pcr` does it the other way round: line 716
is `let tmpl = template.to_string_full().to_ascii_uppercase();` and the
`PcrError::NotDna { what: "template" }` guard is at 717-722 — **three lines
downstream of the slice it was written to protect.** `pl_clone::assembly::assemble`
(assembly.rs:197) has no such guard at all.

I compiled the four functions standalone with `rustc` (no cargo, no `target/`
lock) and enumerated one stray character at each of 17 positions in a 16-base
fixture across five characters: **17 panics, 68 clean, 0 wrong answers.** Minimal
case `Dseq::new("ACGTACGTACGTACGT\u{a0}")` gives watson 18 bytes, crick 22, tail
4, and `end byte index 4 is not a char boundary; it is inside '\u{FFFD}' (bytes
3..6)`. The other 68 placements return `NotDna` correctly. So the defect is
purely the statement ordering, which is a narrower and more credible claim than
"pcr is broken".

*Failure scenario.* A GenBank or FASTA file whose sequence carries one non-ASCII
byte pair among its last few bases — a non-breaking space or micro sign pasted
from a supplier PDF. `pl-fileio` preserves it: genbank.rs:236-240 filters ORIGIN
with `!b.is_ascii_whitespace() && !b.is_ascii_digit()` only, fasta.rs:45 with
`!b.is_ascii_whitespace() && *b != b'*'` only, and `Document::from_bytes`
(doc.rs:663-671) sanitises nothing. A repo-wide grep for `is_ascii()` returns six
non-test hits, none of them a load-time filter. Open the file, go to the Clone
panel, choose PCR, paste any two primers: clone.rs:1353-1356 does
`from_utf8_lossy(&mol.seq).to_ascii_uppercase()` → `Dseq::new` → `pl_clone::pcr`,
`plan` is called synchronously in the panel body on the UI thread
(clone.rs:349/890-892), there is no worker thread and no `catch_unwind` anywhere
in `bins/pl-gui`, and the process aborts with `byte index 4 is not a char
boundary` instead of showing the refusal that was written for this case. Two more
surfaces: `bins/pl/src/main.rs:5570` builds a `Dseq` straight from stdin, and
`crates/pl-design/src/pair.rs:1232` does the same in `pcr_length`.

*Why the tests miss it.* `rg -n '"template"'` returns exactly **one** hit
repo-wide: the construction site at lib.rs:719. Nothing asserts that variant is
ever produced. `a_non_ascii_primer_is_rejected_rather_than_panicking`
(lib.rs:1776) uses `let tmpl = "ACGTACGTACGTACGTACGTACGT"` in all six of its
cases, varying only the primers, so it cannot fail for the template.
`a_crafted_template_does_not_panic` (lib.rs:1749) is a fuzz-shaped loop in which
every template is ASCII. `a_molecule_that_is_not_dna_is_refused_rather_than_cut`
(lib.rs:1359) drives a non-ASCII molecule but only through `cut`/`try_cut`, which
check first; I hand-computed its `NOT_DNA` fixture — w=24, c=28, tail=4,
`crick[..4]` is "TTTT" — so it does not reach the boundary either.

`AUDIT-2026-07` raised this class ("a non-ASCII primer (NBSP pasted from a vendor
sheet) panics on a char boundary") and its remedy note warned that `rc()`'s

"raised but not actually fixed" category.

*Fix.* Move the template's ASCII check ahead of `to_string_full()`, checking
`template.watson` and `template.crick` directly, exactly as `try_cut` does and for

`w−5`; one in the middle of the sequence passes against the unfixed code.
