> **Scope: the running GUI at `7eb0a88`, not the code that produces it.**
>
> Three reviewers drove the installed binary (`%USERPROFILE%\.local\bin\polylinker.exe`,
> 7eb0a88) under three lenses — information architecture, interaction and
> feedback, accessibility and edges — and returned 40 raw findings. This pass
> deduplicated them to 26, re-verified every one ranked high, and killed or
> corrected the ones that did not survive.
>
> **One high finding was refuted outright**, and it was the top-ranked finding
> of one lens. Its suggested fix would have broken crash recovery. **Five more

## How this was verified

Every finding ranked **high** below was re-checked by one of:

- **Execution against the installed binary or the CLI at the same commit.**
  `pl export`, `pl convert` and `pl info --json` run the same `pl-draw`,
  `pl-fileio` and `pl-core` the GUI links, so a disagreement between the

- **Reading the code path end to end**, not grepping for a symbol. The

- **The reviewers' own captures**, re-read rather than taken on trust. Two

Where a claim could not be reached, it is listed under "Not verified" and
carries no rank.

## The one that is not real

### R1. "Crash recovery restores a different molecule, with every coordinate +1" — **REFUTED**

Filed high by the information-architecture lens. The claim: the banner names
`pKoV with His decR.dna`, but what loads is 8,118 bp with nine `primer_bind`
features the `.dna` does not have and every coordinate one higher than the file
(`cat promoter` 7,749..7,851 against 7,748..7,850). Suggested fix: hash the
payload at snapshot time and **refuse to restore a snapshot whose payload does
not match its header**.

Both halves of the evidence have innocent explanations, and the suggested fix
would destroy the feature.

**The nine `primer_bind` features are the `.dna`'s nine primers.** Verified by
execution:

```
$ pl info "pKoV with His decR.dna" --json
  "n_primers": 9, "n_binding_sites": 9, "n_features": 9

$ pl convert "pKoV with His decR.dna" -o rt.gb
      8117 bp  circular     9 feat
$ grep -cE '^     primer_bind' rt.gb/pKoV_with_His_de.gb
  9
```

`recover.rs` stores the snapshot as GenBank *on purpose* — the module doc says
why: "recovery that requires the crashing app is worth very little". GenBank's
only spelling for a SnapGene primer is `primer_bind`. Nine features in, nine
features plus nine `primer_bind` out. The molecule is the same molecule.

**There is no +1 coordinate shift.** The same round trip writes

```
     promoter        complement(7748..7850)
```

— byte-identical to the `.dna`'s 7,748..7,850 as `pl info --json` reports it.
The GenBank writer does not shift anything.

**The 8,118 bp is the user's own edit.** The banner in that capture reads
`1 edit(s)`. A one-base insert before position 7,748 gives 8,118 bp and moves
`cat promoter` to 7,749..7,851 — exactly the observed difference, on every
feature, in one direction. The reviewer compared a snapshot *containing an
unsaved edit* against the file on disk and read the edit as corruption.

**Why the suggested fix is worse than the defect.** A recovery snapshot exists
precisely because it differs from the file on disk. Hashing the payload against
the original and refusing on mismatch would refuse every snapshot that has
anything in it to recover. Do not build this.

What survives from the filing is real but much smaller, and is finding 15 below:
the banner does not say the draft is a GenBank rendering, does not show length
or age, and lists two drafts of one plasmid as two identical undated rows.

## Ranked findings

Ranked by what each buys a plasmid biologist at the bench, not by cost.

### Tier 1 — do these

#### 1. The map names enzymes and never names features — **confirmed**

*Direction: connecting the views.*

`bins/pl-gui/src/map.rs` builds its `RingLabel` list from cut sites only
(map.rs:790-853). `crates/pl-draw/src/lib.rs:667` pushes a `Label` per feature.
So one binary draws two different maps of one file:

```
$ pl export "pKoV with His decR.dna" -o v.svg
      8117 bp  circular    31 label
$ # <text> nodes in the SVG:
  cat promoter · CmR · sacB promoter · SacB · f1 ori · pSC101 ori ·
  Rep101(Ts) · decR · decR his        (9 feature names)
  AflII 271 · SpeI 562 · … · BbsI 7,963  (22 site labels)
```

The GUI map for that file draws **zero** feature names — verified in
`16-topright-icon.png`, `21-feature-type-dropdown.png`, `long-01-features.png`
and `many-01-features-map.png`, across four molecules and both themes.

Identity is therefore carried by colour alone, and pKoV has four duplicate
pairs: white ×2 (`cat promoter`, `sacB promoter`), yellow ×2 (`f1 ori`,
`pSC101 ori`), magenta ×2 (`SacB`, `Rep101(Ts)`), grey ×2 (`decR`,
`decR his`). Colour cannot separate any of them. This is also the one surface
that breaks the project's own rule at `crates/pl-draw/src/contrast.rs:24-29` —
"Colour is never the only channel … a feature has a name".

Two consequences, and the second is the worse one: a plasmid map that does not
name its features is a restriction map; and **the figure Lior exports is not
the figure he proofread**, because the export gains nine labels that were never
on screen.

Reuse `ring::place_ring` with a feature-label pass. If the label budget forces
a choice, features should win by default. Cheapest partial: paint the hovered
feature's name into the status line — that needs no layout at all (see
finding 6, which is the same hover machinery).

#### 2. Closing or replacing an edited document destroys it silently — **confirmed**

*Direction: a fourth thing — the document lifecycle.*

Two paths, one missing guard.

**Window close.** `grep -rni "on_close_request\|CloseRequested\|close_requested\|
allow_close\|ViewportCommand::Close"` over `bins/` and `crates/` returns
**nothing**. eframe 0.35 closes on the title-bar X with no prompt, and
`on_exit` (main.rs:1715-1723) then calls `recover::clear()` unconditionally —
so the autosaved draft goes too. The reviewer reproduced this twice: six bases
typed into pKoV, click X, process gone in under 2.5 s,
`%LOCALAPPDATA%\Polylinker\recovery` empty. I confirmed the directory is empty
now.

**Open… with a dirty document.** `adopt()` (main.rs:1153-1185) assigns
`self.document = Some(d)` with no dirty check anywhere on the path. What makes
this finding sharp is what sits three lines below it: `adopt()` closes the
design panel *with a stated reason*, and closes the feature editor *with a
stated reason*, each with a paragraph of comment explaining that silence there
would let file A's coordinates be written into file B. The document itself —
the only thing holding the user's work — is dropped without a word.

`on_exit`'s comment already contains the argument for the fix: "Quitting is a
durable action like any other, and this one deletes the only copy." It just
never asks.

Add one guard used by both paths, keyed on `document.edited()`: name the
molecule and the edit count, offer Save / Close anyway / Cancel, and on "close
anyway" **keep** the recovery file and say so. This is the only data-loss
defect in the review.

#### 3. The toolbar status describes the wrong operation — **confirmed**

*Direction: connecting the views (one status channel), with a lifecycle half.*

Three defects with one root: `self.status` is written from two places and read
from one.

- `settle()` (main.rs:2359-2373) commits a typing run and **never assigns
  `self.status`**. Only `edit()` (main.rs:2381-2390) does. So typing,
  Backspace and Delete — the edits that change bases — leave the bar showing
  the last discrete action.
- `describe(d.molecule(), d.format)` is called at load (main.rs:1350) and on
  drop-open (main.rs:1804) and **never again**. The toolbar's `8,117 bp` is a
  snapshot of the file as opened; the map caption and the Sequence header are
  live. Reproduced twice with three lengths on screen at once.
- Ctrl+A then Delete destroys every base and every feature with no
  confirmation. `33-seq-delete-all.png` shows the toolbar, next to Undo, still
  reading `add feature UX probe feature — Ctrl+Z to undo` while the actual
  consequence is reported in orange at the bottom of the other panel.

After the most destructive gesture in the app, the most prominent status text
names a harmless earlier action and invites an undo the user will read as
removing a feature. The codebase already has the confirm pattern this needs, at
main.rs:5090 for large pastes.

Set the status from `settle()` using the shape the log already produces
("delete 8,122 bp at 1 — Ctrl+Z to undo"); recompute `describe()` per frame or
relabel it "8,117 bp on disk"; confirm a delete that removes the whole molecule.

#### 4. The sequence view is single-stranded — **confirmed**

*Direction: the amino-acid/ORF track — this is its prerequisite.*

`bins/pl-gui/src/seqedit.rs` has no bottom-strand rendering. The seven
occurrences of "complement" in that file are all documentation or
selection-arc arithmetic; none draws a strand. The only "complement" the GUI
offers is `Molecule > Reverse complement`, which **rewrites the molecule** —
an edit, not a view. The File tab meanwhile reports `strands  double`.

Five of pKoV's nine features are on the reverse strand. Reading a
reverse-strand CDS, checking a reverse primer's 3' end against the template, or
verifying a mutagenesis primer all require mentally reverse-complementing 50-base
rows one at a time. In SnapGene the double-stranded view is the default working
surface.

The reverse-complement logic is in `pl-core`; this is rendering, not
computation. **Do this before the amino-acid track**, not after: a
reverse-strand CDS translated over a top-strand-only view reads backwards.

#### 5. The same plasmid gives two different digests and two different topologies, silently — **confirmed**

*Direction: connecting the views.*

Two independent split-brains, same shape: two surfaces of one app assert
opposite facts and neither says it is assuming.

**Methylation.** `crates/pl-fileio/src/snapgene.rs:264` is the *only* writer of
`Molecule::methylation` in the workspace — verified by grep across
`crates/pl-fileio` and `crates/pl-core`. GenBank and FASTA readers never touch
it, so they get all-false. Open pKoV as `.dna` and BclI is struck through,
tagged "Dam blocked"; open the identical 8,117 bp as `.fa` and BclI is a clean
unique cutter at 6,561 (`v1-fa-enzymes.png` against `05-enzymes-tab.png`). The
File tab omits the methylation row entirely when nothing is set
(main.rs:4838-4849, `if !meth.is_empty()`), so "assumed unmethylated" and "not
recorded" render identically — as nothing. And there is no way to say the DNA
came from a dam⁻ strain, though `OpKind::SetMethylation` exists and
`doc.rs:267` says in as many words: "Nothing in the UI edits the methylation
flags".

Two wrong answers in opposite directions. From an Addgene GenBank the app says
BclI cuts — it will not, in any Dam⁺ prep, and the digest fails at the bench.
From a `.dna` it says BclI is unavailable — but Lior preps from JM110 precisely
to use it, and cannot tell the app so.

*(Note for the fixer: `pl_core::Methylation` carries a fourth flag, `cpg`
(lib.rs:360), which the File tab's three-way array does not report either.)*

**Topology.** `pl_core::Topology` is two variants with `Linear` as
`#[default]` (lib.rs:30-34). `pl_index::Topology` is three, with `Undeclared`
as the default (lib.rs:239) — and carries a comment explaining exactly why:
"FASTA never says, and a Plasmidsaurus assembly of a plasmid arrives as FASTA
at an arbitrary rotation — so reading 'no topology field' as 'linear' loses
exactly the origin-straddling hits that assembly was sequenced to check."
`pl-index` is right and `pl-core` has not been told. So a FASTA is `linear` in
the toolbar and the File tab, and `8,117 bp undeclared … scanned as circular`
in the Library tab, three clicks away.

`pl-core` already applies this reasoning to the neighbouring field —
lib.rs:474-477 on `double_stranded`: "Unknown is a real third state and callers
should say so." Give `Topology` the same third state, render it as "topology
undeclared — drawn linear", and offer a one-click "treat as circular" that logs
an op.

#### 6. Map click, double-click and hover are all implemented and all invisible — **confirmed**

*Direction: connecting the views. Highest value per line changed in the review.*

Everything works. `map.rs:1169-1207` hit-tests in polar space with a carefully
reasoned angle normalisation; main.rs:5062-5088 wires click to select,
double-click to the feature editor and hover to `self.hot`. None of it is
perceptible:

- **No cursor change.** `grep -c "CursorIcon" map.rs` = 0.
- **No tooltip.** One `on_hover_text` in the whole file (map.rs:374), and it is
  not the feature.
- **No echo in the list.** The Features tab paints `rect_filled` for
  `selected` (main.rs:2994-3000) and nothing for `hot`.
- **`hot` is never cleared.** Both assignment sites are guarded —
  `if hot.is_some() { self.hot = hot }` (main.rs:3032) and
  `if hovered_out.is_some() { self.hot = hovered_out }` (main.rs:5072) — so an
  emphasis persists after the pointer has left.
- **Hit target is `band_w * 0.5 + 3.0`** ≈ 7.5 pt radial, against WCAG 2.2
  SC 2.5.8's 24 pt, which the project claims to meet.
- The one visible effect of a successful click is that the right panel jumps to
  the Features tab, which reads as an unexplained tab switch.

Both the capture agent and one reviewer independently concluded the map was
inert. Lior will conclude the same within a minute and stop trying. A shipped
feature is therefore worth zero, on the exact interaction the map exists for.

Set the cursor on `out.hovered.is_some()`; show a hover tooltip with name,
type, span and strand (the sequence view already does this per base); render
`hot` in the list with a lighter fill than `selected`; clear `hot` to `None`.
Four small changes recover a whole feature.

#### 7. A long feature name makes the right-hand panel unusable — **confirmed**

*Direction: connecting the views (robustness of the panel that carries them).*

`long-01-features.png`, re-read for this pass, is worse than the filing
suggests. With a 150-character `/label` in the file:

- The tab strip reads `ce  History  File` — Features, Library, Enzymes and most
  of Sequence are off the **left** edge of the pane.
- The whole `New… / Edit… / Duplicate / Remove` row is gone.
- The coordinates and strand glyphs — the two things a cloner reads off that
  list — are off the right edge of the window.
- The splitter was measured at x=763 and did not move after drags to x=200 and
  x=1200.

Mechanism confirmed in code: main.rs:2956 is a bare
`ui.label(RichText::new(&f.name)…)` with no truncation, no wrap constraint and
no clip, inside the `SidePanel`, so one row's desired width sets the panel's.

`/product` and `/label` values of 60-130 characters are routine in NCBI
GenBank. This is not an exotic input; it is what happens when Lior downloads an
annotated record. Truncate to the pane with the full string on hover, and clamp
the panel's desired content width so one row cannot pin the splitter.

#### 8. In light theme, pale features vanish — and `--check-contrast` says the figure is fine — **confirmed**

*Direction: connecting the views (screen must agree with figure).*

On screen, feature bands are drawn as `Shape::line(pts, Stroke::new(w, b.color))`
(map.rs:1143) — a stroked polyline in the feature's own colour, with **no
outline**. In the export, every band carries `stroke="#2b2f34"
stroke-width="0.6"`, verified in the emitted SVG. So a white feature is a
visible white band in the figure and invisible on the screen.

`16-topright-icon.png` shows it: in light theme `cat promoter` and
`sacB promoter` are white bands on a near-white ring, and their swatches in the
Features list are blank white squares. The dialog's "the file's own colour
always wins" is the right policy for fidelity; nothing guarantees the result is
distinguishable from what it is drawn on.

Separately, `crates/pl-draw/src/contrast.rs`'s `audit()` matches
`Item::Text`, `Item::Circle { stroke }` and `Item::Path { stroke: Some(..) }`,
and drops everything else into `_ => {}`. **It never measures a fill.**
Verified:

```
$ pl export "pKoV with His decR.dna" -o v.svg --check-contrast
pl: contrast ok (WCAG 2.2 AA)
$ # fills in that same figure:
  #22262a ×31, #6b7280 ×10, #993366 ×3, #ffffff ×2, #ffff00 ×2, …
```

Two pure-white and two pure-yellow filled bands passed a check that claims AA.
They happen to be visible because they are stroked — which is luck, not the
check. A PI preparing a figure for a journal with accessibility requirements
takes that sentence as a warrant it is not.

*Correction to the filing:* "four of nine features invisible" overstates it.
The two **white** features are effectively invisible in light theme; the two
**yellow** ones fail the 3:1 ratio numerically but remain perceptible by hue in
`16-topright-icon.png`. The backbone at 2.82:1 is the third real one.

Give on-screen bands the hairline stroke the exporter already uses, and either
extend `audit` to fills or narrow its message to "every label and stroke meets
AA".

#### 9. A keyboard user cannot reach the sequence, and loses Ctrl+Z on their first Tab — **confirmed**

*Direction: a fifth thing — accessibility. Nobody proposed it.*

Two guards, same over-broad test:

```rust
// main.rs:4687, sequence_keys
if ui.ctx().memory(|m| m.focused()).is_some() { return; }
// main.rs:1932, global_shortcuts
let typing = ctx.memory(|m| m.focused()).is_some();
if asking || typing { return Shortcuts::default(); }
```

"Anything is focused", not "a text box is focused". The sequence grid is not a
focusable widget, so it receives keys only when **nothing** has focus — there
is no way to Tab into it — and Ctrl+Z/Ctrl+Y/Ctrl+S/Ctrl+O die the moment any
widget takes focus, which for a keyboard user is the first Tab they press.
Escape restores the no-focus state (egui 0.35 clears `focused_widget` on
Escape), but nothing says so, and Escape everywhere else means cancel.

Measured: Tab ×10 to the History tab, then Right ×5 and `aaaa`, later `acgt` —
zero edits, Undo still greyed (`kbd-14-typed-acgt-keyboard-only.png`). The
reasonable conclusion is that sequence editing requires a mouse.

Test against a set of text-entry ids the app maintains, and make the sequence
grid focusable so Tab reaches it and the focus ring says the caret is live.

> **Correction, 2026-08-13 — one specific above is wrong, and it is the
> mechanism.** "The sequence grid is not a focusable widget ... there is no way
> to Tab into it" was false at `7eb0a88`, the commit reviewed. The grid was
> already allocated `Sense::click_and_drag()`, which in egui 0.35 is
> `CLICK | FOCUSABLE | DRAG`, and `Context::create_widget` puts every focusable
> widget into the tab order. Tab reached it then and reaches it now: measured at
> `189be8a` as the **fifteenth** press from a fresh window, which is why "Tab
> ×10" above landed on the History tab and not on the sequence.
>
> The symptom, the ranking and the requested fix all stand — the finding is not
> withdrawn. What changes is that the defect was **worse** than described. The
> grid was not merely unreachable; it was reachable, and reaching it silently
> switched off every arrow key, every typed base, Backspace, Delete and Ctrl+A
> on the one widget then holding the keyboard, with nothing on screen to say so.
> A fixer who trusted the sentence above would have started by making the grid
> focusable, which it already was, and would have shipped the trap wider.
>
> Corrected in place under this document's own rule for the five findings whose
> specifics were wrong: a reviewer's example is what a fixer reaches for first.

#### 10. Selecting a region answers none of the questions that follow it — **confirmed**

*Direction: surfacing Tm/ORFs — this is that direction's front door.*

The readout is `4..132 · 129 bp`. No GC%, no Tm, no translation, no reverse
complement on the clipboard, and no mark anywhere on the map. GC% exists in the
app only as a whole-molecule figure in the File tab.

The measurement that makes this a build direction rather than a nicety:

```
$ grep -rl "pl_thermo\|pl_gel\|pl_sanger\|pl_abif" bins/pl-gui/src/

$ grep -rn "find_orfs\|pl_core::translate" bins/pl-gui/src/
```

Extend the readout to `4..132 · 129 bp · 47% GC · Tm 61.4 °C (NN, 50 mM Na⁺)`,
gate the Tm on a sane length range, and draw the selection as an arc on the
map — the map already knows how to draw an arc from a coordinate range, and
`grep -c "selection" map.rs` is 0.

#### 11. The enzyme filter governs three surfaces and not the map — **confirmed**

*Direction: connecting the views.*

`self.enzyme_set` reaches the Enzymes list (main.rs:3110-3150), the inline cut
marks (3373-3386) and the "N site(s) hidden" disclosure (4493-4534). The map

#### 12. Feature rows carry no length — **confirmed, example corrected**

*Direction: the amino-acid/ORF track.*

Each row shows extent, kind and a segment count, and never a bp figure
(main.rs:2967-2990). For a CDS the two facts that matter are its length and
whether it is a multiple of three — that is how an in-frame fusion or a His-tag
insertion is checked, which is exactly what this file is (`decR his`,
5,423..5,905). Neither is available anywhere in the app.

*Correction:* the filing's claim that "for a multi-segment feature the extent is
the bounding box, not the feature" does **not** hold for its own example. SacB's
segments are `join(1976..3310,3311..3397)` — contiguous — so the extent span
(1,422 bp) and the segment sum (1,335 + 87 = 1,422) are identical. The row is
not lying about SacB. And the origin-crossing case the filing implies was
already fixed in the 2026-07-29 audit: main.rs:2972 calls
`f.extent(span, circular)`, not `start()`/`end()`. What is genuinely missing is
the number itself, plus `(3n)` or an aa count.

Also confirmed: the filter matches `f.name` and `f.kind` only
(main.rs:2940-2942) — not qualifiers, which is how features are actually named
in GenBank — and shows no match count.

#### 13. The feature dialog — **confirmed, two claims corrected**

*Direction: accessibility, plus the aa track.*

Verified in `21-feature-type-dropdown.png`, `18b-badcoord-zoom.png` and
`19b-letters-zoom.png`:

- **Title is an index.** "Feature 4" beside a Name field reading "f1 ori".
- **The Type dropdown shows 8 of 17.** `KINDS` (featedit.rs:91) has 16 entries
  plus `other…`; the `ComboBox` at featedit.rs:1076 takes egui's default popup
  height, and the capture shows it stopping dead after `primer_bind`. egui's
  scrollbar fades at rest, so it reads as a complete list.
  *Correction:* one lens reported that `misc_feature` is **absent** from the
  dropdown. It is present — tenth in `KINDS` — and merely below the fold. The
  a11y lens got this right and the IA lens did not. The consequence is the
  same (a user editing one of pKoV's two `misc_feature`s sees no way back to
  it) but the fix is a `.height()` call, not a list change. Move `other…` to
  the top while there.
- **Coordinates are coerced silently.** Typing 99,999 into the start of
  `f1 ori` leaves the field showing `99999` while the prose below reads
  "Segment 1 runs from 8,117 forward through base 1 to 4,399 — 4,400 bp", and
  the "crosses origin" box has ticked itself as a consequence of the clamp.
  Typing `abc` is displayed and ignored the same way.
  *Correction:* the **model is not corrupted** — egui clamps correctly, and the
  prose beneath is true. The defect is that the field text and the committed
  value disagree with no error styling and no refusal, in an app whose CLI
  names the number when it refuses. Reconcile the field on focus-out and say
  "99,999 is past the end; this molecule is 8,117 bp".
- **Escape does not close it.** No Escape handler in `featedit.rs` or
  `design.rs` (grep: 0); both use `egui::Window`, and in egui 0.35 only
  `egui::Modal` consumes Escape — the app's one `Modal` is the paste consent at
  main.rs:5341. What Escape does instead is clear focus, so the next keystroke
  goes nowhere. Non-modality is defended in the module docs and the defence is
  sound; cycle Tab within the window rather than letting focus reach the
  `Remove` button behind it.
- **A checkbox labelled "aa"** whose own hover text says "Nothing in this
  program reads it." A biologist reads that as "show the translation". Relabel
  it, and note that it becomes meaningful the moment the aa track lands.

#### 14. Feature names are absent from the sequence view at the default layout — **confirmed**

*Direction: connecting the views.*

`seqedit.rs:140`: the name gutter appears only when

gutter. At the default splitter the row is 50 columns and the gutter is

#### 15. The recovery banner withholds what would let you choose — **confirmed** (this is what survives R1)

*Direction: the document lifecycle.*

`recovery_banner()` (main.rs:841-861) formats title, op count and original
path. `recover::Snapshot` carries `saved_at` (recover.rs:45-51) and it is never
displayed; neither is the molecule's length. Entries are not de-duplicated by
original path, so two drafts of one plasmid render as two textually identical
undated rows — reproduced by two reviewers independently.

The restore path (main.rs:891-910) calls `Document::from_bytes`, so the
restored document has an **empty op log**: Undo is greyed and the "1 edit(s)"
the banner advertised cannot be inspected or reversed. And the banner never
says the draft is a GenBank rendering in which `.dna` primers arrive as
`primer_bind` features — the representation change that produced R1.

Show `saved_at` as a relative age and the length on each row (the code already
sorts by `saved_at`); say the draft is a GenBank snapshot and what that carries;
say that the edits are restored but the undo history is not. The prose that is
already there — "These are copies. Your original files were not modified." —
is the standard the rest of the banner should meet.

#### 16. The dirty dot does not mean unsaved, and there is no plain Save — **confirmed, one claim corrected**

*Direction: the document lifecycle.*

`doc.rs:229`: `edited() = !log.all_ops().is_empty()`. `wrote()`
(main.rs:1505-1511) only sets the transient status. So the dot means "edits
exist" and is on forever after the first one, saved or not. There is no way to
answer "is my work on disk?", and the only record of a save is a status line
the next action replaces.

The Save menu offers GenBank and FASTA only (main.rs:2030-2046). There is no
plain overwrite-Save. `pl_fileio::snapgene::write` exists (snapgene.rs:783), so
the round trip a SnapGene user needs — open `.dna`, annotate, hand the `.dna` to
a student — is impossible, and the only way out is a format the app itself
warns is lossy.

*Corrections:*
- **PNG and TIFF export do not exist.** `grep -rl "png\|tiff" --include=*.rs`
  over `crates/` and `bins/` returns **nothing**. The suggestion to "surface the
  existing PNG/TIFF writers" would send a fixer looking for code that was never
  written, whatever the task list says. **EPS does exist**
  (`crates/pl-draw/src/eps.rs`, reachable as `pl export --eps`) and is the only
  one of the three that can be surfaced today.
- **"Saving through Polylinker destroys the cloning history" is not true
  today.** snapgene.rs:817 does decline to write block 7, and says why: it is a
  provenance graph and "inventing a SnapGene history node claiming a provenance
  this file does not have would be a fabrication" — a defensible refusal. But
  the `.dna` writer is unreachable from the GUI, so no user can currently lose
  anything this way. The finding becomes real the moment "SnapGene .dna…" is
  added to the Save menu, and the warning should land in the same change.

#### 17. The Library is unreachable until a document is open, and its results are inert — **confirmed**

*Direction: connecting the views.*

main.rs:2596-2600 returns "Nothing open." before the tab dispatch, so it
swallows `Tab::Library` — which holds its own state in `self.scan` and needs no
molecule. The Library is the only cross-file search in the app and, since there
is no in-document search either (see the corrections section), **the only
sequence search that exists anywhere**. The first thing a PI does is "where did
I put that plasmid?", and that is exactly the state in which the feature that
answers it refuses.

Clicking a result does nothing, so a search that locates which of 348 files
contains a 25-mer leaves the user to find that file by hand through Open…

Exempt `Tab::Library` from the gate; make a result row open the document,
landing the caret on the first hit.

#### 18. History is a changelog, not a history — and the `.dna`'s real history is announced and withheld — **confirmed**

*Direction: connecting the views.*

`history_tab()` (main.rs:3304-3334) builds every row from `ui.label()`. Nothing
is clickable, so an abandoned branch is shown, named "(other branch)" and
cannot be reached. There are no timestamps, and the op text never names what
was inserted ("insert 12 bp at 10" — which 12?). `Document::seek()` already
exists.

*Correction, from the interaction lens and confirmed here:* the "▶" is **not** a
broken disclosure triangle. It is `HISTORY_HERE`, the cursor marker for the
current row. Nothing in the tab was ever clickable, which is a bigger finding
than a dead expander — but "make the triangle expand" is the wrong fix. Change
the glyph so it does not read as an expander, and make the rows travel.

Meanwhile the File tab announces "A cloning history tree is present."
(main.rs:4871-4877) — the record of how the construct was actually built, which
is the provenance question a plasmid biologist actually asks — with no way to
see it. Two things called history, and the one named in the tab bar is the one
he rarely wants, in a vocabulary (hashes, branches) from another discipline.

#### 19. Genome scale: an empty picture, an uncountable enzyme table, and no way to travel — **confirmed**

*Direction: connecting the views, plus a fourth thing — navigation.*

Directly relevant to the metaproteomics and *F. nucleatum* work.

- A 4.6 Mb FASTA draws a bare ruler: no caption, no features, no ticks, and no
  sentence saying why — while the same molecule's Enzymes tab lists 58 enzymes
  with thousands of sites. This is not even the "This file describes nothing to
  draw." message (main.rs:5036), which at least explains itself. On a plasmid
  the map is scrupulous about what it dropped; here it discloses nothing.
- The Enzymes tab shows "58 cut more than once" with **no unique-cutter heading
  at all**, so zero and omitted are indistinguishable, and truncates each row's
  position list with "…" while never printing the site count — the only number
  that matters at this scale.
- No go-to-base, no map zoom (`grep -i zoom map.rs` = 0; no `goto`, no `Key::F`
  anywhere in the GUI). Ctrl+End moves the caret without scrolling to it. Nine
  large wheel bursts covered 2.4% of the molecule.

Lior will conclude the app cannot handle genomes, when it parses and digests one
in about a second. Say why the map is empty, print the site count, always print
the unique-cutter heading, and add a go-to-base box — which also solves the
keyboard-only case in finding 9.

#### 20. The same failure at feature density — **confirmed**

*Direction: connecting the views.*

At 9,000 features over 200 kb the map is seven concentric rings of unreadable
stripes and the caption still speaks only about enzymes: "0 of 58 cutters
labelled · 1 dual, 57 multi not drawn". Nothing says how many features were
drawn, how many lanes were used, or that none is labelled. The Features filter
narrows the list and leaves the map untouched.

The Sequence tab does the right thing on the same file — "features overlap 6
deep; 3 lanes are drawn and the rest are counted in the row's +N" — which is
exactly the sentence the map is missing. Copy it.

### Tier 3 — real, small

#### 21. The window title is always "Polylinker" — **confirmed**

*Direction: connecting the views.*

Verified in every capture including `long-01-features.png`: the OS title bar
carries the literal string with no filename and no dirty marker, and the app
runs several instances all titled the same. At 900×650 the filename also
vanishes from the toolbar and the map caption elides to "pKo…", so nothing on
screen or in the taskbar says which file is open. Comparing pKoV v1/v2/v3 side
by side — the commonest plasmid-work pattern — becomes guesswork.

The toolbar's elision order is deliberate and documented (main.rs:2113-2145);
the OS title is simply never set.

#### 22. The linear map's axis ends one base past the molecule — **confirmed**

`map.rs:535-541`: `tick_pos` is
`(((span as u128 * i as u128) / 10) as u64).saturating_add(1)`, so `i = 10`
yields `span + 1` — 8,118 on an 8,117 bp molecule, 4,641,653 on a 4,641,652 bp
one. On a circular molecule that is the origin and defensible; on a linear one
that base does not exist, and a coordinate printed on a map in a cloning tool is
quoted at face value. In the same row the enzyme labels butt together
("4,760BglII", "5,464BamHI") and the leftmost is clipped to "419SphI" — and
every FASTA opens linear (finding 5).

#### 23. Undo does not clear the warning it reverses — **confirmed in code, not re-run**

`do_undo()` clears `self.notice` but not `self.edit.notice`; `seqedit::restore()`
does not either; `clear_notice()` fires only on the next keystroke. So the
orange "cat promoter, CmR, sacB promoter and 7 more removed — they described
bases that no longer exist. Ctrl+Z to undo." survives the undo that reversed it
(`37-primer-design-panel.png`), telling the user in warning colour that features
are missing when they are not, and pointing at a Ctrl+Z that would now undo
something else. Key the notice to the log cursor it was raised at.

#### 24. Absences that read as failures — **confirmed**

Five of six tabs have carefully written empty states — "No edits yet…"
(main.rs:3274), "No folder yet." (2655), "Nothing open." (2598), "This file
describes nothing to draw." (5036), "There is nothing here to edit."
(seqedit.rs:280). The Features tab has none: on a FASTA it renders the button
row and an empty filter box over a blank panel, so "this file has no
annotations" and "the app failed to read them" look identical. The File tab
likewise omits the methylation and primers rows rather than stating them.
An absent row and a zero are different claims.

#### 25. Two accessibility measurements — **not independently re-measured**

Leader lines use `theme.rs`'s `faint` (#b8c2c8 light, #4a555c dark), reported at
1.75:1 and 2.29:1. When four labels stack in a column (SphI 4,758 / NsiI 4,760 /
BglII 4,886 on pKoV) the leader is the only thing tying a name to a tick, and
misreading it means digesting at the wrong coordinate. Darkening the last few
pixels at the tick would fix the association without a heavy line.

`Palette::selection()` is the accent at alpha 30/255, reported at 1.20:1 with no
second channel — no edge bar, no border, no weight change — and the map shows
the selection not at all (finding 10). In light theme the selected row is more
visible than that number suggests (`16-topright-icon.png`); in dark theme it is
not. Add a non-colour cue.

The theme toggle (main.rs:2096, `egui::global_theme_preference_switch`) is the
only unlabelled control in the app, and one click on it pins the app away from
"follow the system" with nothing recording that a preference was taken. It is
also the control that triggers finding 8.

#### 26. "1 not searchable" is unattributable — **not verified**

The Library index summary reports the count and nothing names the record or the
reason, so a negative search result is not trustworthy. The search footer's own
provenance line is exemplary by contrast — "347 of 348 searched, 1 past the size
cap, 344 containing ambiguity codes" — which is why this one number stands out.

## What was checked and found fine

Worth recording, because several of these are unusual enough that a redesign
could remove them by accident.

**The disclosure culture is the best thing in this app.** The primer panel
prints three caveats — specificity checked against this template only,
hairpin/dimer energies are a perfect-helix screen and therefore printed as "or
more stable" rather than a value, the 200-per-side cap is a bound on the search
and not a criterion. The Library footer reports 347 of 348 searched, 1 past the
size cap, 344 with ambiguity codes, 345 undeclared and scanned as circular. The
File tab says 40% of the `.dna` is a regenerable cache. Every finding above
about a silent assumption is a place where **this** standard was not applied,
not a place where a new standard is needed.

**Lossy-save reporting.** "FASTA keeps only the bases; this drops 9 feature(s)
and the topology (it will reopen as linear)" and "3 feature(s) written as
forward; GenBank cannot express their strand" — reproduced live in this pass:

```
$ pl convert "pKoV with His decR.dna" -o rt.gb
pl: 3 feature(s) have no GenBank-expressible strand and are written as
    forward: pSC101 ori, decR, decR his
```

Both name the count *and* the consequence.

**Coordinate and origin handling.** "8,117 bp circular — coordinates are 1-based
and inclusive" at the top of the dialog; "insert at 1 · before base 1, at the
origin · every feature's coordinates shift" against "insert at 8,118 · after
base 8,117 · numbering unchanged"; the "take the other arc (7,988 bp)" button;
and the crossing explanation that spells out both readings of one pair —
"Untick 'crosses origin' to read the same two numbers the other way round
(4,399..8,117)". This is the part of plasmid software most often quietly wrong,
and here it is correct and taught.

**Strand is never carried by colour or glyph alone.** `featedit.rs` builds every
strand option as glyph *and* word and offers all four states including
Unoriented. pKoV has three unoriented features (`pSC101 ori`, `decR`,
`decR his`, confirmed via `pl info --json`); a two-state toggle would have
corrupted them.

**Rejected input is named, not swallowed.** "3 characters ignored: x, z, 9",
with the sticky-notice logic written specifically so a fast typist's rejected
character is not erased by the next accepted one.

**Panels that stop being valid close with a reason**, and the comments at
main.rs:1169-1183 record that the alternative silently wrote file A's
coordinates into file B.

**Autosave never touches the original**, and says why: "An editor that quietly
rewrites the original every few minutes has turned 'close without saving' into a
lie."

**Undo narrates its side effects** — "undone — the origin was put back too".

**Typing coalesces**: 12 keystrokes become one history entry.

**Performance is a non-issue.** A 4.64 Mb genome opens in ~1 s; its Enzymes tab
renders in under a second; a 116,042-row sequence view scrolls without a dropped
frame; 9,000 features over 200 kb opens in about a second; primer design over
4,020 candidates and 40,000 pairs returns in under a second. Every problem at
scale in this review is navigation or disclosure, never speed.

**Focus is visible and correctly ordered** where it works: the ring measures
9.03:1 against the focused button's fill, and Tab steps over greyed Undo/Redo.

**Phosphor is used on exactly two controls** (Undo/Redo), always beside the
word, with the reasoning written down. No icon in this app carries meaning
alone.

**The Enzymes tab answers the digest question at plasmid scale**: unique vs
multi split, recognition sites, positions, strike-through plus a text tag
("Dam blocked", "1-site") so the state survives a monochrome screenshot.

## Where each finding belongs

Three build directions were proposed. The review found that a fourth and a
fifth are needed, and that one proposed direction has an unmet prerequisite.

**A — connecting the views** (map ↔ sequence ↔ features ↔ enzymes ↔ library):
findings **1, 6, 11, 14, 17, 18, 20, 21**, the map half of **10**, and the
consistency half of **5**. This is the largest cluster and contains the single
highest-value change in the review.

**B — the amino-acid / ORF track**: findings **4** (its prerequisite — build the
complement strand first), **12** (length and 3n), and the `aa` checkbox in
**13**. Note the correction above: the orchestrator's list says the complement
strand exists. It does not.

**C — surfacing gel / traces / ORFs / Tm**: finding **10**, which is the front
door. The measurement that makes this a direction rather than a wish is that
`pl-thermo`, `pl-gel`, `pl-sanger` and `pl-abif` have **zero** references in the
GUI — four crates already written, tested and shipped, reachable only from a
terminal.

**D — a fourth thing nobody proposed: the document lifecycle.** Findings
**2, 3, 15, 16**. Close, open-over, save, dirty state, recover. This is not a
view and not a track; it is the contract about when the user's work is safe. It
contains **the only data-loss defect in the review** (finding 2), and it is
invisible to any review that only looks at what is drawn. If one thing from this
document gets built first, it should be finding 2 — not because it is the most
valuable, but because it is the only one whose absence costs work that cannot be
got back.

**E — a fifth thing: accessibility and edge robustness.** Findings **7, 8, 9,
13, 19, 22, 24, 25**. The project already claims WCAG 2.2 AA and already ships a
contrast module; three of these are places where the claim outruns the code
(**8** most sharply, where `--check-contrast` prints a pass it did not earn),
and two are input classes that make the app unusable rather than merely awkward
(**7**, a long `/label` from NCBI; **9**, a keyboard).
