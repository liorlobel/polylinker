### LENS: Completeness critic — what the dossier never asked: sustainability, governance, users, safety/biosecurity, accessibility, i18n, correctness metrology, and the null hypothesis that the right deliverable is not an app
VERDICT: The dossier is genuinely excellent at everything researchable from a desk — the .dna byte layout, the licence graph, the algorithm provenance, the component inventory — and structurally blind to everything about running a project that real people depend on. Seven area reports, roughly thirty thousand words, and not one mention of biosecurity screening, accessibility, internationalisation, crash reporting, autosave, bulk migration, parser security, support burden, fiscal hosting, or key custody. It has also never argued its own null hypothesis. Three specific things should change before any roadmap is committed. First, the flagship differentiator is gone: three areas nominate a .dna writer as the wedge while a fourth reports sgffp shipped one, MIT-licensed and round-trip-verified against SnapGene 8.2.2, in June 2026 — verify that claim in an afternoon, and if it holds, the unclaimed ground is not the format at all but the openly-licensed common-features database, which has no incumbent, is legally the one place where copying creates real exposure, and would improve every tool in the field at once. Second, the credibility plan is inverted: JOSS will not publish a GUI, and the citable, fundable, field-serving artifact is a cdseguid-based public truth set of cloning operations that any tool can run — build the benchmark before the app, not after. Third, the money assumption is stale: CZI EOSS cycle 6 is closed with no successor and NLnet's open funds are payments and fediverse hosting, so 'we will get a grant' is not currently a plan, and the live alternatives (Wellcome and Kavli directly, ELIXIR, biosecurity philanthropy tied to a Common Mechanism integration, sponsorship from parties with a commercial stake in a free design tool) each imply a different product shape and should be chosen before the architecture is. My overall read: the strongest version of this project is probably not a SnapGene clone at all. It is an openly-licensed annotation database, a correctness benchmark, and a well-factored engine with CLI and MCP surfaces — three artifacts that are individually publishable, individually adoptable by the incumbents, and collectively harder to make obsolete than any desktop app. If an app is still wanted afterwards, it will be much cheaper to build on top of them, and much easier to justify.

- NO CORRECTNESS METROLOGY: ALL THREE PROPOSED QA LAYERS COMPARE REPRESENTATIONS, NOT MOLECULES. Golden-file diffing, differential parsing against Biopython/bio-parsers, and property-based tests all assume you can tell whether two tools produced the same construct — but for a circular double-stranded plasmid, rotation, strand choice, annotation order and feature-name spelling are all free, so byte-diffs and GenBank diffs produce false failures and mask real ones. The missing primitive exists and is unmentioned: `seguid` 0.2.1 (MIT, Björn Johansson — the pydna author, released 2025-07-27) implements lsseguid/csseguid/ldseguid/cdseguid, where cdseguid gives a rotation- and complement-invariant checksum for circular double-stranded DNA. Make cdseguid the assertion primitive in every cloning test. Then go further and build the thing this field has never had: a public truth set of (input sequences, operation, expected cdseguid) triples covering digests, ligations, Gibson junctions, Golden Gate overhang sets, PCR products, origin-spanning edits and frame arithmetic — derived from published constructs with wet-lab-confirmed sequences. That artifact is more citable than the app, is usable by SnapGene, Benchling, pydna, UGENE and plascad alike, is publishable in a venue that will actually take it, and is the only way to substantiate 'we are correct' rather than 'we are free'.
- NO HAZARD TIERING, SO QA EFFORT CANNOT BE ALLOCATED. 'A wrong answer is fatal to the project' appears in five area reports; nowhere is there a ranked list of which computations are dangerous and why. Build one, because it drives both test budget and UI design. Tier 1 (silent, expensive, hard to notice at the bench): cut sites hidden by the active enzyme-set filter — the one documented case of a month of lost bench time; methylation-blocked sites (dam/dcm/EcoKI); Type IIS overhang identity and ligation-fidelity prediction in Golden Gate; coordinate arithmetic across the origin of a circular molecule; reading frame after an indel edit; enzymes that need two sites to cut efficiently (SgrAI, NarI, SacII, BspMI, BsgI, Type IIB). Tier 2 (wrong but caught quickly): auto-annotation calls, ORF boundaries, Sanger discrepancy calls. Tier 3 (approximate by nature, users expect drift): Tm, agarose band position, codon-optimization scores. Tier 1 items should be adversarially fuzzed, differentially tested, and rendered LOUD in the UI — never display a digest without stating what is filtered out, never assert Golden Gate success without showing the full overhang set and its single-mismatch neighbours. Tier 3 items should ship a visible 'method and parameters' popover with the citation, so a discrepancy with SnapGene reads as a documented modelling choice rather than a bug. The dossier's instinct to chase Tm parity 'to the decimal' is misallocated effort against this ranking.
- NOBODY DECIDED WHO OWNS THE PROJECT, WHO ANSWERS THE EMAIL, OR WHAT HAPPENS WHEN THE FIRST MAINTAINER LEAVES. The landscape area establishes that every dead project in this space died of maintainer attrition, then mitigates with 'a governance doc and 2+ maintainers'. That is not a plan. Missing decisions, each of which is cheap now and near-impossible later: a fiscal/legal host so that code-signing certificates, domains, the updater signing key and any grant money are held by an entity rather than a person (NumFOCUS, Open Collective Foundation, Software Freedom Conservancy, or the Open Bioinformatics Foundation, which is the closest cultural fit and already hosts Biopython); a support channel that is not GitHub Issues, because bench scientists email and post to forums and will not open an issue; a triage rota and an explicit response-time promise you can actually keep; a documented handover/archival policy so the project dies gracefully rather than rotting; and a decision on whether contributions require a CLA or DCO before the first outside PR arrives. The legal area raises Bar-Ilan IP assignment — correctly — but never joins it to the question of what entity the project belongs to afterwards.
- ACCESSIBILITY APPEARS NOWHERE IN ROUGHLY THIRTY THOUSAND WORDS. A plasmid map is a colour-coded diagram and the sequence view is a dense text grid — this is close to the worst case for accessibility, and no competitor has solved it, which makes it a differentiator as well as an obligation. Concretely: adopt a CVD-safe default feature palette (Okabe–Ito or equivalent) with redundant non-colour encoding — arrow shape, hatching, border style, always-on labels — because roughly 1 in 12 men cannot reliably separate a red AmpR arrow from a green CDS, and 'unique cutters are shown in bold' is currently the only non-colour channel in the whole design. Beyond colour: WCAG 2.2 AA contrast in both light and dark themes, and verify that the dark theme survives SVG/PDF export rather than producing a black-background figure; full keyboard operation of the sequence editor, which must be designed in from the start; and a deliberate screen-reader model, since reading 4,000 bases aloud is useless — the right semantics are navigate-by-feature, announce-by-region, with base-level detail on demand. Also: funders increasingly ask, and institutional procurement in the US and EU increasingly requires an accessibility statement (VPAT/EN 301 549), which is a soft blocker for exactly the pharma and core-facility deployments the dossier hopes to reach.
- INTERNATIONALISATION IS UNEXAMINED EVEN THOUGH THE DOSSIER TRANSCRIBED THE EVIDENCE. 'Localization' is listed verbatim as one of SnapGene's 45 user-guide sections and nobody asked what is in it or which languages ship (the support section returns 403 to automated fetch; the marketing features page mentions no languages at all, which is itself a signal that localisation is under-marketed rather than absent). This matters more than it looks. The largest under-served user populations for a free tool are almost certainly not anglophone, and the teaching market — where a free tool should win outright — is global. Practical items nobody raised: strings must be externalised from commit 1, because retrofitting i18n into a React app plus an SVG label-layout engine is brutal; the .dna feature/primer/notes payloads are UTF-8 XML, so non-Latin feature names are a real round-trip test case that no existing parser test covers; CJK text metrics break naive SVG label collision-avoidance; RTL layout matters for a Hebrew/Arabic user base and is directly relevant to a Bar-Ilan-based project; and number/date formats leak into exported maps and reports. Decide now whether v1 is English-only-but-i18n-ready, and say so.
- THE 'LAST 10%' LIST IS MISSING ITS MOST EXPENSIVE ITEMS. Installers, code signing, notarization and the updater are well covered; the following are not mentioned at all. (1) Crash reporting that does not break the privacy promise — opt-in, symbolicated, self-hosted (GlitchTip/Sentry self-host); without it you are blind, with it done wrong you contradict your only marketing claim. (2) Autosave and crash recovery — losing an afternoon of annotation is a one-strike uninstall. (3) File-association conflict with the SnapGene that is already installed on the same machine: both claim .dna, and silently stealing the association will enrage exactly the user you are courting. Ask, don't take. (4) OS-level touches that make a tool feel real: Quick Look / Explorer thumbnail previews rendering the plasmid map, and Spotlight/Windows Search indexing of sequence and feature text. (5) Concurrent-edit conflicts on Dropbox/OneDrive/Google Drive — the dossier's local-first pitch quietly assumes a single writer, and labs are not single-writer; you need file locking or conflict detection or you will silently lose edits (note SnapGene shipped a Google Drive file-performance fix in 8.2.0, so this is a known real-world pattern). (6) BULK MIGRATION, which is the actual switching cost: a lab has thousands of .dna files in a shared drive, and 'import folder, deduplicate, index, search across all of them' is more decisive than any editor feature. (7) An in-app 'this answer looks wrong' button that captures the input file and the operation, because that is how tier-1 correctness bugs will actually reach you.
- THE PARSER IS TREATED AS A CORRECTNESS PROBLEM AND NEVER AS AN ATTACK SURFACE. A .dna file is untrusted binary that arrives by email from a collaborator, and per the dossier's own block table it contains LZMA-compressed history and modifier blocks, zlib-compressed XML attachments, BGZF/BAM trace alignments, and multiple XML payloads — that is decompression bombs, XML entity expansion, and attacker-controlled 4-byte big-endian length fields feeding allocations and index arithmetic. Round-trip fuzzing is proposed; security fuzzing is not. Add: cargo-fuzz/AFL against the parser as a memory-safety and resource-exhaustion target; hard caps on decompressed size and per-block allocation; XML parsed with entity expansion and external entities disabled; and refuse-with-error rather than allocate-on-trust for implausible lengths. Related and equally unmentioned: the Tauri/Electron shell threat model (CSP, IPC surface, disabling remote/node integration), and custody of the updater signing key — Tauri's updater signature 'cannot be disabled', which means that one key compromise pushes arbitrary code to every install, and an unfunded project with the key in a personal GitHub account is a soft target. Key custody belongs with the fiscal host, in a hardware-backed or CI-only secret, with a documented rotation procedure.
- THE AI QUESTION, ANSWERED RATHER THAN LEFT OPEN. Verified: SnapGene's features page contains no reference to AI, ML or LLMs, while the closed freemium newcomer PlasmidStudio leads with AI annotation. My read is that AI as a runtime feature inside a cloning simulator is a distraction and an active liability — the product's single asset is trust in deterministic, reproducible answers, and a plausible-looking hallucinated annotation or 'suggested' cloning strategy is precisely the silent-wrong-answer failure mode the dossier fears most, delivered at scale. Two AI-adjacent moves are cheap and genuinely differentiating. First, ship an MCP server / typed tool surface over the deterministic engine so agents can drive real operations: SnapGene's entire programmatic surface is two CLI commands and no API, 'limited API' is a named community complaint, and the space is empty — the only Addgene MCP server in existence is a 6-star hobby repo (longevity-genie/addgene-mcp, MIT, last pushed 2025-06-20). This costs a week on top of a well-factored library and reaches the computational-lab audience that a GUI never will. Second, use LLMs offline in the build pipeline rather than at runtime: triaging candidate features, drafting provenance-tagged descriptions, and cross-checking the open annotation database — the single largest work item in the project — with mandatory human review and a signed-off column. Adopt the rule: AI may propose, never assert; nothing AI-derived ships without provenance and a human sign-off.
- THE NULL HYPOTHESIS — THAT THE RIGHT DELIVERABLE IS NOT AN APP — IS NEVER ARGUED, DESPITE THE DOSSIER ASSEMBLING ALL THE EVIDENCE FOR IT. ove-electron accumulated roughly 1,600 desktop installs in 3.5 years; DnaFeaturesViewer, a matplotlib plotting library, has 694 stars against OVE's ~100; JOSS will not publish a GUI; the .dna writer is apparently already solved by sgffp; and the one thing that demonstrably does not exist anywhere is an openly-licensed common-features annotation database. Three non-app shapes deserve to be costed before a single line of GUI is written. (i) THE DATABASE AS THE PRODUCT: a versioned, per-feature-provenanced (source_db, accession, licence, curator, date, DOI) CC-BY or CC0 annotation set plus its public build pipeline, replacing the SnapGene-derived data that pLannotate and half the ecosystem quietly depend on. It would improve pLannotate, OVE, seqviz, plascad, OpenCloning, SpliceCraft and potentially Addgene simultaneously, has no incumbent, is legally clean, is highly citable, and is the single highest-leverage contribution available. (ii) THE ENGINE AS THE PRODUCT: pydna plus the correctness truth set plus CLI and MCP surfaces, letting the several existing UIs compete on top. (iii) UPSTREAM CONTRIBUTION AS THE PRODUCT: fund the React-19/Blueprint-6 migration in tg-oss, contribute jsonToSnapgene to @teselagen/bio-parsers, and package OpenCloning for the desktop — which the dossier itself names as 'the highest-leverage thing an outside team could do' and then does not adopt as the plan. If an app is still the answer after costing these, that decision is much stronger for having been argued.
- NOBODY ASKED THE USERS, AND CHEAP QUANTITATIVE PROXIES WERE NEVER TRIED. Every area report flags this: Reddit blocked or accessed through a mirror with 5-15 upvote threads, one Hacker News thread with 24 comments, and a workflow-frequency ranking explicitly labelled 'inference'. The entire product thesis rests on that. Before architecture: 20-30 structured interviews with bench scientists across a PI, postdoc, grad student and core-facility spread, asking specifically what would make them switch and what they last got wrong. And the unattempted quantitative work: conda/PyPI/npm download curves for pydna, snapgene_reader, plannotate, @teselagen/ove and seqviz as an ecosystem-size proxy; asking Addgene directly for the .dna-versus-GenBank download split, which would settle how load-bearing .dna actually is; counting university software-catalogue listings as an institutional-penetration proxy; YouTube tutorial view counts; and the volume of SnapGene crack/keygen search traffic as a direct unmet-demand signal. Two populations were not examined at all: non-anglophone users (the Chinese-language molecular biology community is large and was never searched), and the teaching market — SnapGene gives course licences to professors for free precisely because it is the acquisition funnel, and it is the one segment where a free tool should be able to win outright and permanently.
- NO DOCUMENTATION PLAN, AND NO STRATEGIC CONTINGENCY PLAN. On documentation: the only mention is a user complaint that a README was written for developers. The audience is a first-year graduate student, which means the four documentation modes (tutorial, how-to, reference, explanation) should be planned explicitly; docs must ship offline inside the app, because a local-first tool whose help requires internet contradicts itself; every computation needs a methods page stating the exact algorithm, parameters and citation, which doubles as the answer to 'why is your Tm different from SnapGene's'; and video matters more than anyone wants to admit — SnapGene's tutorial library is a real moat and the cheapest part of it to match. On contingency: the dossier notes the EULA and the format can change, but never asks what happens if Dotmatics/Siemens responds. Three plausible moves would each neutralise a different pillar of the plan — a free tier that includes editing (kills the 'we beat the free Viewer' positioning), publishing the .dna spec or an official SDK (kills the interop wedge and, worse, arrives wrapped in an NDA that would contaminate anyone who accepts it), or shipping a real scripting API (kills the strongest computational-lab argument). Write down now which parts of the strategy survive each, because the durable advantages — data ownership, offline operation, openness, an open annotation database, an auditable correctness suite — are the ones that survive all three, and they are not currently what the roadmap leads with.
